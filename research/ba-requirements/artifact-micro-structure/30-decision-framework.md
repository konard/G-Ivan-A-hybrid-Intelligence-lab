# Рамка принятия решений: выбор структуры и её проверка

## 1. Порядок принятия решений

Решения принимаются в объявленном порядке; каждое следующее не может отменить
предыдущее. Порядок существен: сегодня формат выбирается первым и неявно, и
именно поэтому он утягивает за собой состав разделов.

| Шаг | Решение | Вход | Кто решает |
| --- | --- | --- | --- |
| 1 | Продуктовый класс и atomic function | задача, продуктовый каталог спицы | БА, машинно проверяется наличие привязки |
| 2 | Профиль (`P-*`) | продуктовый класс | выводится из каталога, БА подтверждает |
| 3 | Скелет | закрытый словарь слотов | **не выбирается**: один для всех |
| 4 | Класс формата (`F-*`) | адресат и стадия | БА объявляет во входе прогона |
| 5 | Проекция (`V-*`) | аудитория поставки | объявляется, может быть несколько |
| 6 | Заполнение слотов | ядро | навык |

Правило `DF-1`: **шаги 1, 2, 4 и 5 объявляются до генерации**. Незаявленный
формат — источник класса `F-MIXED`, который в корпусе встретился трижды.

## 2. Выбор класса формата

| Вопрос | Ответ | Класс |
| --- | --- | --- |
| Артефакт покидает команду? | нет | `F-SHORT` |
| Адресат принимает решение о согласовании? | да | `F-APPROVAL` |
| Артефакт является основанием для разработки? | да | `F-CLASSIC` |
| Артефакт отвечает на исследовательский вопрос, а не задаёт требования? | да | `F-NARRATIVE` |

Правило `DF-2`: **`F-APPROVAL` и `F-CLASSIC` — проекции одного ядра, а не
разные документы**. Если для согласования потребовалось написать текст,
которого нет в ядре, нарушен инвариант `MI-1`, и это дефект ядра, а не
особенность согласования.

Правило `DF-3`: класс `F-NARRATIVE` **не производит требований**. Документ этого
класса не может быть входом разработки; попытка сослаться на него как на ФТ —
машинно обнаружимый дефект (в нём нет идентификаторов требований).

## 3. Распределение проверок по гейтам

Критерий `К` макро-модуля: проверка машинна, если её результат определяется
сопоставлением с фактом вне модели. Ниже — применение критерия к микро-уровню.

| Проверка | Гейт | Обоснование по `К` |
| --- | --- | --- |
| Все обязательные слоты присутствуют | `G-mach` | сопоставление с закрытым словарём |
| Подписи совпадают с каноническими | `G-mach` | сравнение строк |
| Пустой обязательный слот имеет причину из словаря | `G-mach` | сравнение с закрытым списком |
| Разделов `S-OTHER` нет | `G-mach` | отображение по `SLOT_RULES` |
| Каждое требование ссылается на строку `S-SCOPE` | `G-mach` | проверка идентификаторов |
| Каждому требованию соответствует сценарий и критерий | `G-mach` | проверка `S-TRACE` |
| Глубина нумерации соответствует классу формата | `G-mach` | разбор идентификаторов |
| Утверждение в `S-FR` не описывает поведение интерфейса | `G-self` | требует чтения смысла, факта вне модели нет |
| Требование не описывает существующую функциональность | `G-human` | требует знания системы, необратимо по последствиям |
| Достаточность объёма для согласования | `G-human` | ценностное суждение адресата |

Правило `DF-4`: проверка объявляется машинной только если для неё существует
исполнимый валидатор. Правило, записанное в тексте методологии без валидатора,
считается рекомендацией — вывод, подтверждённый историей `P2` в
[`tools/validate-rrp-links.sh`](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/blob/main/tools/validate-rrp-links.sh),
где правило соблюдалось в 3 модулях из 8, пока не стало машинным.

## 4. Golden Set как часть гейта `G-mach`

Постановка issue #561 закрывает вопрос о статусе эталона: Golden Set —
**обязательный элемент** гейта, а не альтернатива схеме. Разделение
ответственности:

| Компонент гейта | Что проверяет | Форма |
| --- | --- | --- |
| Схема слотов | наличие, порядок, подписи, причины пустоты | машинный валидатор |
| Чек-лист | правила `R-1`…`R-6`, глубина нумерации, трассируемость | машинный валидатор |
| Golden Set | как выглядит правильно заполненный слот | 1–2 эталона на продуктовый класс |

Правило `GS-1`: **эталон не является входом генерации сам по себе**. Он
используется двояко: как few-shot образец на входе и как образец структуры при
сравнении на выходе. Правило `GS-2`: расхождение с эталоном по **структуре** —
отказ гейта; расхождение по **содержанию** — не отказ, иначе эталон
воспроизводится вместо решения задачи.

### 4.1. Когда эталон синтезируется

Замер (§6 датированного отчёта) показал, что корпус `runs/` не даёт ни одной
чистой продуктовой выборки: продуктовая разметка множественная, почти каждый
документ помечен почти каждым классом, и группы «несколько документов одного
класса с согласованной структурой» не существует. Индукция по истории
невозможна, поэтому синтез — не запасной вариант.

Правило `GS-3`: эталон синтезируется, если для продуктового класса в корпусе
нет **двух** документов с совпадающим скелетом. Правило `GS-4`: синтетический
эталон получает статус `draft` и не применяется как few-shot образец до
подтверждения человеком; до подтверждения он работает только как структурный
образец. Правило `GS-5`: происхождение эталона (исторический или
синтетический) объявляется во frontmatter и не скрывается — иначе синтетика
незаметно становится нормой.

## 5. Критерии готовности микро-уровня

| ID | Критерий | Как проверяется |
| --- | --- | --- |
| `К-M1` | Словарь слотов и подписей закрыт и опубликован в Хабе | наличие артефакта нормы |
| `К-M2` | Валидатор структуры документа исполним и включён в CI | прогон на корпусе |
| `К-M3` | На группе документов одной задачи совпадение скелетов = 1.0 | повторный замер |
| `К-M4` | Для каждого продуктового класса спицы есть ≥ 1 эталон | пересчёт по каталогу |
| `К-M5` | Доля разделов `S-OTHER` в новых документах = 0 | повторный замер |

`К-M3` и `К-M5` — точки фальсификации: если после внедрения словаря скелеты
по-прежнему расходятся, причина расхождения не в отсутствии словаря, и рамка
подлежит пересмотру, а не расширению.
