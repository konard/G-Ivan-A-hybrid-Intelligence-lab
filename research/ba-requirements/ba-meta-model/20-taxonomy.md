# Таксономии: четыре канонические и одна служебная

## 1. Правила таксономии

| Правило | Формулировка |
| --- | --- |
| `T-1` | Таксономия закрыта: значение вне словаря — отказ на входе, а не молчаливое расширение. |
| `T-2` | Расширение словаря выполняется задачей с указанием случая, который не покрылся; «на будущее» словарь не расширяется. |
| `T-3` | Каждое значение имеет ровно одно каноническое имя; синонимы объявляются отображением, а не вторым значением. |
| `T-4` | Значение таксономии наследуется, если у него есть индустриальный источник; собственное значение вводится только при отсутствии аналога и помечается как адаптация. |
| `T-5` | Таксономия принадлежит Хабу по форме, спице — по каталогу значений предметной области. |

## 2. Таксономия артефактов

Ось идентичности: **класс артефакта**. Классы `A-*` наследуют классы целевых
документов `DC-1`…`DC-9` модуля `M2`
([`artifact-rendering/20-taxonomy.md`](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/blob/main/research/ba-requirements/artifact-rendering/20-taxonomy.md))
и дополняют их тремя классами, без которых сквозной маршрут не описывается:
вход, ядро и след.

| Класс | Имя | Роль в маршруте | Источник |
| --- | --- | --- | --- |
| `A-IN` | Входной артефакт | вход маршрута: расшифровка встречи, письмо, тендерное ТЗ, заявка | `M0` |
| `A-CORE` | Ядро требований | размеченное ядро, из которого собираются проекции | `M1`, `DC-9` |
| `A-FR` | Функциональные требования | результирующий документ | `DC-1`, ISO/IEC/IEEE 29148 SRS |
| `A-TZ` | Техническое задание | результирующий документ | `DC-2`, ГОСТ 34.602-2020 |
| `A-US` | Пользовательские истории | результирующий документ | `DC-3`, INVEST |
| `A-UC` | Сценарии использования | результирующий документ | `DC-4`, Cockburn |
| `A-SPEC` | Техническая спецификация | результирующий документ | `DC-5`, 29148 SyRS |
| `A-BCREQ` | Бизнес-требование к изменению | результирующий документ, носитель вертикального среза | `DC-6` |
| `A-DIAG` | Диаграмма (UML/BPMN) | производный артефакт | `M2` |
| `A-REP` | Аналитический или оценочный отчёт | производный артефакт | `DC-8`, BABOK Solution Evaluation |
| `A-TRACE` | След прогона | служебный артефакт: `Trace` в материальной форме | `M4`, `MM-3` |

**Правило `A-0`.** Артефакт, не отнесённый ни к одному классу, не является
выходом шага: он либо черновик внутри шага, либо дефект объявления.

## 3. Таксономия операций

Ось идентичности: **тип работы**. Словарь унаследован из
[`mango_ba_prompts/docs/taxonomy.md`](https://github.com/G-Ivan-A/mango_ba_prompts/blob/main/docs/taxonomy.md)
целиком (`T-4`) и не переизобретается. Колонка «покрытие» — измеренная
([отчёт](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/blob/main/research/ba-requirements/2026-09-08-meta-model-inputs-facts.md), §4),
а не назначенная.

| Операция | Что делает | Типовой выход | Покрытие промптами спицы |
| --- | --- | --- | --- |
| `ingestion` | превращает сырой вход в форму, пригодную для анализа | `A-IN` | есть |
| `understanding` | извлекает термины, цели, неявные допущения, формирует вопросы | глоссарий, список вопросов | есть |
| `modeling` | структурирует требования в модели (UC, US, UML/BPMN) | `A-UC`, `A-US`, `A-DIAG` | есть |
| `solution_design` | прорабатывает системно-технические требования и варианты | `A-SPEC` | есть |
| `documentation` | оформляет результат в целевой документ | `A-FR`, `A-TZ`, `A-BCREQ` | есть |
| `validation` | проверяет полноту, непротиворечивость, тестируемость | `A-REP` | есть |
| `quality` | оценивает качество артефактов и промптов, собирает метрики | `A-REP` | **нет** |
| `research` | изучает предметную область, рынок, практики | `A-REP` | **нет** |
| `governance` | поддерживает правила, статусы, жизненный цикл | служебный | **нет** |
| `impact_analysis` | оценивает влияние изменения на существующие требования | `A-REP` | **нет** |
| `reverse_requirements` | восстанавливает требования из системы или поведения | `A-FR` | **нет** |
| `risk_analysis` | выявляет и оценивает риски требований и решений | `A-REP` | **нет** |
| `release_readiness` | проверяет готовность требований к релизу | `A-REP` | **нет** |

**Факт, определяющий приоритет.** Семь операций из тринадцати не имеют ни
одного промпта. Это не пробел словаря, а измеренная граница исполнимости:
объявленная операция без навыка исполняется человеком целиком, и в маршруте
она обязана быть помечена как `Actor=human`, а не как автоматизированный шаг.

## 4. Таксономия процессов

Ось идентичности: **порядок операций, дающий результат**. Словарь унаследован
из спицы (девять процессов) и дополнен колонкой выходного артефакта, которой в
источнике нет.

| Процесс | Что включает | Ключевые операции | Целевой выход |
| --- | --- | --- | --- |
| `fr-generation` | от сырого запроса до черновика ФТ/ТЗ | `ingestion`, `understanding`, `documentation`, `solution_design` | `A-FR`, `A-TZ` |
| `fr-validation` | проверка готовых ФТ/ТЗ | `validation`, `quality` | `A-REP` |
| `tender-analysis` | разбор внешнего тендерного ТЗ | `ingestion`, `understanding`, `validation`, `risk_analysis` | `A-REP` |
| `uc-us-modeling` | преобразование требований в UC и US | `modeling`, `understanding` | `A-UC`, `A-US` |
| `uml-bpmn-visualization` | построение диаграмм процессов и взаимодействий | `modeling`, `documentation` | `A-DIAG` |
| `po-pm-support` | резюме встреч, письма, уточняющие вопросы | `understanding`, `documentation` | `A-REP` |
| `statistics` | сбор и агрегация статистики по артефактам | `quality`, `ingestion` | `A-REP` |
| `impact-analysis` | оценка влияния изменений на продукт | `impact_analysis`, `reverse_requirements` | `A-REP` |
| `risk-analysis` | оценка рисков требований и готовности к релизу | `risk_analysis`, `release_readiness`, `validation` | `A-REP` |

**Факт, определяющий приоритет.** В поле `process:` метаданных 67 прогонов
встретился **один** процесс из девяти; остальные 65 значений — метки задач.
Словарь процессов существует, но не используется для идентификации работы,
поэтому первым машинным правилом Execution Package становится обязательность
поля `process` из закрытого словаря (`EP-R1`,
[`30-decision-framework.md`](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/blob/main/research/ba-requirements/ba-meta-model/30-decision-framework.md)).

## 5. Таксономия продуктов

Ось идентичности: **предмет, о котором требование**. Таксономия
**унаследована, а не изобретена** (`T-4`) и вынесена из исследования в чистый
справочник Хаба:
[`standards/product-taxonomy-reference.md`](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/blob/main/standards/product-taxonomy-reference.md).
Здесь — только её роль в мета-модели.

```text
L0  Индустриальный базис (TM Forum SID/eTOM, BABOK, IREB, UNSPSC)
 └─ L1  ИТ / телеком
     └─ L2  Domain → Capability            (каталог значений — спица)
         └─ L3  Feature → Atomic Function  (каталог значений — спица)
```

| Правило | Формулировка |
| --- | --- |
| `PT-1` | Продуктовый класс объявляется до начала шага (`MM-4`), а не выводится из текста артефакта. |
| `PT-2` | Хаб владеет формой уровней, спица — каталогом значений (`T-5`). |
| `PT-3` | Требование связывается с уровнем `Feature` или `Atomic Function`; связь только с `Domain` считается неполной разметкой. |
| `PT-4` | Продуктовый класс определяет **профиль заполнения** слотов документа, но не состав скелета (правило `R-3` [микро-модуля](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/blob/main/research/ba-requirements/artifact-micro-structure/20-taxonomy.md)). |

**Факт, определяющий приоритет.** Домен продукта объявлен в метаданных 5
прогонов из 67, а лексические маркеры дают более одного домена у 66 прогонов.
Без `PT-1` продуктовая привязка артефакта невосстановима, поэтому она вносится
в контракт входа, а не в рекомендации.

## 6. Реестр депрекации: режимы запуска

| Значение | Прежняя роль | Статус | Новая роль |
| --- | --- | --- | --- |
| `stepwise` | режим запуска промпта, часть имени артефакта (10 промптов) | `deprecated` | historical evidence |
| `oneshot` | режим запуска промпта, часть имени артефакта (9 промптов) | `deprecated` | historical evidence |
| `legacy` | режим запуска промпта, часть имени артефакта (5 промптов) | `deprecated` | historical evidence |

| Правило | Формулировка |
| --- | --- |
| `DP-1` | Ни одна из четырёх канонических таксономий не содержит режима как класса. |
| `DP-2` | Новый активный артефакт не содержит `stepwise`/`oneshot`/`legacy` в имени, идентификаторе или поле маршрута. |
| `DP-3` | Историческая ссылка на режим в датированном отчёте, прогоне или иммутабельном документе легитимна и не правится. |
| `DP-4` | Форма взаимодействия выражается полем `interaction` маршрута (`dialog` \| `single-pass`), которое не участвует в идентичности навыка. |

Решение, его основания и альтернативы —
[ADR-013](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/blob/main/docs/adr/2026-09-adr-013-run-modes-deprecation.md).
Ссылки на режимы в шести исследовательских модулях Хаба остаются как контекст:
`DP-3` разрешает их, а сквозной рефактор заведён задачей `B-150`.

## 7. Служебная таксономия: гейты и контракты

Таксономия служебная, потому что описывает не предмет работы, а её контроль,
и потому не входит в четыре канонические.

| Гейт | Исполнитель | Что проверяет | Стоимость ошибки |
| --- | --- | --- | --- |
| `G-self` | агент | самопроверка по чек-листу навыка до выдачи результата | дешёвая, обратимая |
| `G-mach` | валидатор | схему, обязательные слоты, подписи, ссылки, Golden Set | дешёвая, детерминированная |
| `G-human` | человек | смысл, продуктовые решения, приёмку | дорогая, необратимая |

| Правило | Формулировка |
| --- | --- |
| `GT-1` | Порядок гейтов всегда `G-self → G-mach → G-human`: человек не тратится на то, что ловит валидатор. |
| `GT-2` | Гейт `fail-closed`: непройденный гейт останавливает маршрут, а не помечает артефакт предупреждением. |
| `GT-3` | Гейт без объявленного контракта запрещён (`MM-2`). |
| `GT-4` | Человеческие гейты `HG-0`…`HG-8` конвейера — именованные экземпляры `G-human`, а не второй словарь. |

| Контракт | Предмет | Источник |
| --- | --- | --- |
| `C-IN` | вход маршрута: объявлен продукт, задача, источник | `M0`, `MM-1`, `MM-4` |
| `C-CORE` | ядро требований | [`solution-modeling/`](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/blob/main/research/ba-requirements/solution-modeling/00-introduction.md) |
| `C-OUT` | результирующий документ и его структура | [`artifact-rendering/`](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/blob/main/research/ba-requirements/artifact-rendering/00-introduction.md), микро-структура |
| `C-CL` | замыкание обратной связи | [`feedback-and-evolution/`](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/blob/main/research/ba-requirements/feedback-and-evolution/00-introduction.md) |
| `C-RK` | маршрут и его прослеживаемость | [`orchestration/`](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/blob/main/research/ba-requirements/orchestration/00-introduction.md), `MM-3` |

## 8. Границы таксономий

- Словари операций и процессов унаследованы из одной спицы. Их полнота для
  другой предметной области не проверялась.
- Классы `A-*` покрывают артефакты БА-конвейера и не покрывают артефакты
  смежных ролей (архитектура, тестирование, поддержка).
- Колонки «покрытие» и «факт» датированы коммитом `8cbf82a`: на другом коммите
  числа будут другими.
