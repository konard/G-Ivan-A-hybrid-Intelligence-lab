# Рамка решений `M3`: контракт `C-CL`, гейты `HG-6`/`HG-7`, калибровка

## 1. Контракт `C-CL`

```yaml
closure:
  id: CL-2026-0031
  out_ref:                       # CL-1
    id: OUT-2026-0031
    version: 2
    core_version: 5
  route_ref: RK-2026-0031
  axes: { a1: [fr, tz], a2: paid-change, a3: L2, a4: hybrid, a5: us, a6: external-contract }
  metrics:                       # только ключи словаря MK-* (CL-4)
    mk.elements_total: 84
    mk.elements_analyst_decision: 11
    mk.drift_added: 0
    mk.drift_lost: 0
    mk.modality_flags: 2
    mk.review_edits: 7
    mk.gate_returns: 1
    mk.cost_tokens: not-measured        # CL-5, а не пропуск
    mk.cost_human_minutes: 240
    mk.elapsed_hours: 31.5
    mk.measurement_method: "manual-timesheet + ND-report"   # CL-6
  external_events:               # CL-2
    - { class: FB-3, at_days: 4, summary: "заказчик снял 2 замечания по срокам хранения" }
    - { class: FB-5, at_days: 62, elements: ["FR-014"], change_type: CH-1 }
  changes:
    - { element: FR-014, type: CH-1, attributed_to: M1 }
  gate:
    hg6: { owner: "БА", decision: closed, basis: "поставка принята, немедленный контур завершён" }
    hg7: { owner: "владелец процесса", decision: pending, due_days: 90 }
  append_only: true              # CL-3
```

### 1.1 Условия приёмки `C-CL`

| № | Условие | Проверка |
| --- | --- | --- |
| `CX-1` | `out_ref` существует и содержит `core_version` | машинная |
| `CX-2` | все ключи `metrics` зарегистрированы в словаре `MK-*` | машинная |
| `CX-3` | каждое поле словаря присутствует либо равно `not-measured` | машинная |
| `CX-4` | `mk.measurement_method` непуст | машинная |
| `CX-5` | `external_events` — список, возможно пустой, но поле обязательно | машинная |
| `CX-6` | каждое изменение в `changes` имеет тип `CH-*` и атрибуцию слою | машинная |
| `CX-7` | запись не изменяется после закрытия `HG-6`; исправление — новая запись со ссылкой | машинная (append-only) |
| `CX-8` | ни одно поле не содержит идентификатора исполнителя как объекта оценки | машинная (запрет `M3-R7`) |

**Ответ на `RQ-3.1`.** Минимальный состав записи — привязка к поставке, ядро
метрик с честными `not-measured`, метод измерения, список внешних событий
(возможно пустой) и решение гейта. Всё остальное — расширения.

**Ответ на `OQ-2` («что считать успехом прогона»).** Успех не является полем
записи. Он вычисляется постфактум как функция от внешних событий и изменений:
работа успешна, если `mk.drift_added = 0`, `mk.drift_lost = 0` и доля элементов
с `CH-1`/`CH-2` не превышает порога, откалиброванного каналом `CA-1`.
Самооценка исполнителя не участвует — это прямое следствие `DF-4`.

## 2. Гейты

| Гейт | Смысл | Машинное предусловие | Владелец |
| --- | --- | --- | --- |
| `HG-6` | закрытие работы | `CX-1`…`CX-6`, `CX-8`; поставка принята на `HG-5` | БА (`internal`), руководитель направления (`external-contract`, `regulated`) |
| `HG-7` | закрытие отложенного наблюдения | истёк `due_days` либо получено событие `FB-5`…`FB-8`; запись дополнена новой версией по `CX-7` | владелец процесса |

**Почему `HG-7` отделён.** `HG-6` закрывает работу, `HG-7` закрывает **знание
о работе**. Совмещение делает длинный горизонт ненаблюдаемым: как только работа
закрыта, никто не возвращается к ней через два месяца. Отдельный гейт с
`due_days` — единственный механизм, дающий данные для `FB-5`…`FB-8`.

## 3. Применение осей

| Ось | Влияние на `M3` |
| --- | --- |
| `A1` | набор форм определяет, какие `ME-2` метрики применимы (`custom-form` добавляет покрытие формы) |
| `A2` | контекст задаёт ожидаемую волатильность: `tender-rfp` заведомо выше, чем `internal-product`; сравнение метрик допустимо только внутри одного значения `A2` |
| `A3` | уровень строгости — главный предмет калибровки (`CA-1`); метрики разных уровней не сравниваются напрямую |
| `A4` | режим исполнения сравнивается по `mk.drift_added` и стоимости — это проверка `H2.3` |
| `A5` | глубина исследования калибруется по volatility (`CA-2`) |
| `A6` | контур задаёт владельцев `HG-6`/`HG-7` и допустимость `due_days` |

**Правило `M3-R6`.** Метрики сравниваются только при совпадении `A2` и `A3`.
Сравнение работы уровня `L1` во внутреннем продукте с работой `L3` в тендере
не имеет смысла и является самой частой ошибкой такой статистики.

## 4. Алгоритм закрытия

```
1. Принять C-OUT; проверить, что HG-5 закрыт (иначе закрывать нечего).
2. Собрать ядро метрик; всё неизмеренное пометить not-measured (CL-5).
3. Указать метод измерения для каждой группы (CL-6).
4. Зафиксировать внешние события немедленного и короткого горизонта.
5. Проверить CX-1..CX-8. Нарушение CX-8 — блокирующее.
6. Закрыть HG-6. Запись становится неизменяемой.
7. Установить окно наблюдения due_days (по умолчанию 90).
8. При поступлении FB-5..FB-8 — новая версия записи со ссылкой на предыдущую,
   классификация изменений по CH-*, атрибуция слою.
9. По истечении окна или по событию закрыть HG-7.
10. Передать агрегаты в каналы калибровки CA-1..CA-5.
```

## 5. Калибровка: как решение меняет правило (`RQ-3.5`)

| Канал | Условие срабатывания | Изменение | Кто утверждает |
| --- | --- | --- | --- |
| `CA-1` | доля элементов с `CH-1`/`CH-2` на уровне `L1` устойчиво выше, чем на `L2`, при сопоставимом `A2` | поднять минимум моделей для соответствующего класса работ | владелец процесса |
| `CA-2` | работы с `A5 = none` показывают большую volatility по `CH-1` | сделать `A5 = us` обязательным для этого класса `A2` | владелец процесса |
| `CA-3` | `mk.drift_added > 0` встречается только при `RM-2` | запретить `RM-2` на уровне `L1` тоже | владелец процесса |
| `CA-4` | доля `mk.gate_returns > 0` после закрытия гейта высока для контура | сменить владельца гейта по `A6` | владелец процесса |
| `CA-5` | повторяющиеся споры о формулировках (`FB-3`) | пополнить словарь модальностей `M2` | БА |

**Правило `M3-R8`.** Изменение правила требует не менее 10 сопоставимых
записей (`A2`, `A3` совпадают) и объявляется как изменение версии
соответствующего модуля. Порог 10 — экспертный и сам подлежит калибровке;
это объявляется честно, а не выдаётся за статистическую обоснованность.

## 6. Запреты

**`M3-R7`.** Метрики `M3` не применяются к оценке исполнителей — ни человека,
ни модели как «сотрудника». Обоснование конструктивное, а не этическое: как
только запись о закрытии влияет на оценку исполнителя, поля `not-measured`
исчезают, а `mk.drift_added` стремится к нулю за счёт занижения проверок.
Разомкнутый контур лучше, чем контур с искажёнными данными, потому что второй
даёт ложную уверенность.

**`M3-R9`.** Ни одна метрика `M3` не является целевым показателем сама по себе;
целевыми могут быть только величины, прошедшие тест из §4 файла
`10-theory.md` (неулучшаемость без улучшения объекта).

## 8. Build vs buy

| Кандидат | Что закрывает | Вердикт |
| --- | --- | --- |
| Существующий контракт прогонов Mango | носитель записи, уже есть в спице | база для `C-CL`; требует фиксации словаря |
| Jira/трекер | события, изменения, время | закрывает `ME-3`, не закрывает `ME-1` |
| GQM как метод | вывод метрик из целей | принять как метод, не как инструмент |
| BI/дашборды | агрегация `ME-4` | преждевременно: нет сопоставимых данных |
| Готовые метрики DORA | образец состава | неприменимы напрямую к БА |

**Вердикт.** Покупать нечего: дефицит не в инструменте агрегации, а в
существовании сопоставимых записей. Первая работа `M3` — словарь и схема, а не
дашборд.
