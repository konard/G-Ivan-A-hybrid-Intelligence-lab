# Рамка решений `M4`: контракт `C-RK`, маршрутизатор, `HG-0` и `HG-8`

## 1. Контракт `C-RK` (маршрутный лист)

```yaml
route:
  id: RK-2026-0031
  input_ref: IA-2026-0031        # C-IA с гейта G6 модуля M0
  template: RT-C                 # типовой маршрут или custom
  axes:
    a1: [fr, tz]
    a2: paid-change
    a3: L2
    a4: hybrid
    a5: us
    a6: external-contract
  axes_basis:                    # основание каждого значения (RQ-4.2)
    a1: "запрос заказчика: ФТ и ТЗ"
    a2: "работа в рамках оплачиваемого изменения по договору №..."
    a3: "внешняя поставка, но не регулируемая"
    a4: "объём допускает пакетную сборку с остановками на гейтах"
    a5: "сценарии нужны, конкурентный анализ не требуется"
    a6: "приёмка на стороне заказчика"
  gates:                         # RT-3: владелец у каждого
    - { id: HG-0, owner: RO-1, state: closed }
    - { id: HG-2, owner: RO-1, state: closed }
    - { id: HG-3, owner: RO-1, state: closed }
    - { id: HG-4, owner: RO-2, state: closed }
    - { id: HG-5, owner: RO-2, state: open }
    - { id: HG-5.1, owner: RO-2, state: pending }
    - { id: HG-6, owner: RO-2, state: pending }
    - { id: HG-7, owner: RO-4, state: pending }
    - { id: HG-8, owner: RO-4, state: available }
  changes:                       # RT-4
    - { axis: a3, from: L1, to: L2, reason: "выяснилось, что поставка внешняя", at_gate: HG-2 }
  state:                         # RT-6
    last_closed_gate: HG-4
    interruption: { class: IN-2, since_days: 3, waiting_for: "ответ по срокам хранения" }
  outputs:
    core_ref: CORE-2026-0031
    out_ref: null
    closure_ref: null
```

### 1.1 Условия приёмки `C-RK`

| № | Условие | Проверка |
| --- | --- | --- |
| `CR-1` | все шесть осей заданы | машинная |
| `CR-2` | комбинация осей удовлетворяет `C1`–`C6` | машинная |
| `CR-3` | у каждого гейта маршрута есть владелец | машинная |
| `CR-4` | `axes_basis` непуст для каждой оси | машинная |
| `CR-5` | каждое изменение оси имеет причину и гейт | машинная |
| `CR-6` | `A3` в `changes` не убывает | машинная |
| `CR-7` | `input_ref` указывает на `C-IA`, прошедший `G6` | машинная |
| `CR-8` | при `interruption` заполнены класс и условие возобновления | машинная |
| `CR-9` | у закрытой работы `outputs.out_ref` либо решение `HG-8` заполнены | машинная |

**Ответ на `RQ-4.1`.** Минимальный состав маршрутного листа — ссылка на вход,
шесть осей с основаниями, список гейтов с владельцами, журнал изменений осей,
наблюдаемое состояние и ссылки на выходы. Всё остальное — расширение.

## 2. Маршрутизатор: спецификация

```
ВХОД: C-IA (проверенный инициирующий артефакт)
ВЫХОД: C-RK либо отказ с причиной

1. Извлечь кандидатов значений осей из C-IA:
   A1 — по запрошенным документам; A2 — по типу отношений;
   A6 — по адресату поставки; A5 — по наличию сценарной неопределённости.
2. Значения, не выводимые из входа, помечать unknown, НЕ угадывать.
3. A3 назначить по правилу M4-R4 (см. §3), не по умолчанию.
4. A4 предложить по объёму и уровню: L3 → исключить autonomous-oneshot.
5. Проверить совместимость C1–C6.
   Конфликт → §4: разрешение по приоритету, при неразрешимости — ES-2.
6. Подобрать типовой маршрут RT-A..RT-F по близости комбинации;
   при отсутствии совпадения — custom с явным перечнем гейтов.
7. Назначить владельцев гейтов по A6 (правила M1 §3.1, M2 §4, M3 §2).
8. Заполнить axes_basis. Оси со статусом unknown выносятся человеку на HG-0.
9. Проверить CR-1..CR-7. Закрыть HG-0.
10. Только после этого разрешена первая генерация (RT-1).
```

**Правило `M4-R4` (назначение `A3`).** Уровень строгости определяется по
наиболее строгому из трёх признаков: внешность поставки (`A6`), необратимость
последствий (договорные обязательства), наличие нормативного контроля.
Значение по умолчанию отсутствует намеренно: умолчание превращается в
фактический выбор, сделанный никем.

## 3. Применение осей

| Ось | Роль в `M4` |
| --- | --- |
| `A1` | определяет, какие слои и формы обязательны; `custom-form` включает `M2-R4` |
| `A2` | выбирает типовой маршрут `RT-A`…`RT-F` и задаёт группу сравнения для метрик `M3` |
| `A3` | определяет обязательность гейтов, допустимые режимы рендера и уровень следа |
| `A4` | определяет число точек остановки, а не объём работы модели (`M4-R1`) |
| `A5` | определяет включение исследовательских шагов в `M1` |
| `A6` | определяет владельцев всех гейтов и необходимость `HG-5.1` |

## 4. Совместимость и конфликты (`RQ-4.4`)

Правила `C1`–`C6` RFC проверяются машинно. При конфликте применяется приоритет
`M4-R5`, согласованный с `M1-R9`:

```
регулирование (A6 = regulated)
  > договорное обязательство (A2 = contract | paid-change, A6 = external-contract)
    > требование строгости (A3)
      > предпочтение режима (A4)
        > глубина исследования (A5)
          > состав форм (A1)
```

**Разрешение конфликта — всегда в сторону большей строгости.** Пример: `A3 = L1`
при `A6 = regulated` разрешается повышением `A3` до `L3`, а не ослаблением `A6`.
Если приоритет не даёт однозначного ответа, срабатывает эскалация `ES-2` к
владельцу процесса; молчаливого выбора маршрутизатор не делает.

## 5. Гейты `M4`

| Гейт | Смысл | Машинное предусловие | Владелец |
| --- | --- | --- | --- |
| `HG-0` | назначение маршрута | `CR-1`…`CR-7`; все `unknown` разрешены человеком | `RO-1`; при `ES-2` — `RO-4` |
| `HG-8` | остановка работы | зафиксированы причина, потраченная стоимость и то, что остаётся пригодным | `RO-4` |

**Почему `HG-8` принадлежит `RO-4`, а не исполнителю.** Остановка — решение о
списании затрат; исполнитель, принимающий его сам, оказывается судьёй
собственной работы. Одновременно `HG-8` объявлен **правом**: его доступность
(`state: available`) обязана присутствовать в каждом маршруте, иначе
`RT-7` вырождается в «любая работа обязана дойти до поставки».

## 6. Контракт прерывания и возобновления (`RQ-4.5`)

```
ПРЕРЫВАНИЕ:
1. Записать все незаписанные контракты (C-RK обязательно, C-CORE при наличии).
2. Указать класс IN-1..IN-5, причину и условие возобновления.
3. Зафиксировать last_closed_gate.
4. Всё, что существует только в диалоге, считать утраченным (M4-R3).

ВОЗОБНОВЛЕНИЕ:
5. Прочитать C-RK; восстановить оси и владельцев.
6. Проверить, не изменились ли основания осей (axes_basis) за время паузы;
   при изменении — RT-4 с причиной, повышение A3 допустимо, понижение нет.
7. Проверить, не устарела ли версия C-CORE относительно последней поставки.
8. Продолжить с гейта, следующего за last_closed_gate.
9. При IN-4 (смена исполнителя) новый исполнитель обязан перепройти HG-2
   как приёмку границ — это единственный гейт, повторяемый при передаче.
```

**Правило `M4-R6`.** Возобновление после `IN-3` (аварийная остановка) требует
пометить элементы ядра, затронутые причиной остановки, статусом не выше `AS-2`:
доверие к незакрытому не переживает аварию автоматически.

## 7. Что `M4` передаёт слоям

| Кому | Что |
| --- | --- |
| `M1` | `C-RK`: оси, владельцы `HG-2`/`HG-3`/`HG-4`, глубина `A5` |
| `M2` | `C-RK`: формы `A1`, уровень следа по `A3`, режим по `A4`, владелец `HG-5`/`HG-5.1` |
| `M3` | `C-RK` + телеметрия `TL-1`…`TL-4` как основа `ME-3`; группа сравнения по `A2`/`A3` |
| От `M3` обратно | калибровка `CA-2`, `CA-4`: значения `A5` по умолчанию и владельцы гейтов |
| Спице (Mango) | предложение, а не правка: см. [§6 файла `40-practice-and-cases.md`](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/blob/main/research/ba-requirements/orchestration/40-practice-and-cases.md) |

## 8. Сводный вердикт build vs buy по конвейеру

| Компонент | Кандидаты | Вердикт |
| --- | --- | --- |
| Хранение ядра (`M1`) | StrictDoc, Doorstop, Sphinx-Needs | **buy** — StrictDoc, пилот обязателен |
| Рендер в ГОСТ-формы (`M2`) | шаблонизаторы + Pandoc | **buy инструмент, build слой прообразов** |
| Проверка недрейфа (`M2`) | готовых нет | **build** — процедура `ND` |
| Запись о закрытии (`M3`) | контракт прогонов Mango | **extend** — расширение существующего |
| Агрегация и дашборды (`M3`) | BI-инструменты | **отложить** — нет сопоставимых данных |
| Маршрутный лист (`M4`) | BPMN/CMMN-движки, Temporal, LangGraph | **build** — YAML-артефакт, движок избыточен |
| Проверка совместимости осей (`M4`) | движки правил (DMN) | **buy опционально** — таблица решений DMN подходит |
| Телеметрия стоимости (`M4`) | API-телеметрия провайдера, трекер | **buy** — `TL-1`, `TL-2` |

**Общий принцип вердикта.** Покупается всё, что связано с хранением, рендером и
телеметрией; собственной разработкой остаётся только то, что выражает
специфический предмет конвейера — связь смысла с документом (`ND`, прообразы) и
маршрутный лист как лёгкое обязательство. Ни один из рассмотренных движков
процессов не оправдывает своей цены для контура, где единица работы —
предпроектная задача аналитика.
