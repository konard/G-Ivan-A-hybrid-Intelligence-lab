# Рамка решений `M1`: контракт `C-CORE`, оси `A1`–`A6`, гейты, build-vs-buy

> **Модуль.** Файл `30-decision-framework.md` модуля
> [`research/ba-requirements/solution-modeling/`](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/tree/main/research/ba-requirements/solution-modeling).
> Всё, что здесь описано, — **предложение**, а не действующая норма: `M1` не
> редактирует стандарты спицы (правило `P.8` RFC).

## 1. Контракт `C-CORE` (выходной контракт `M1`)

Ядро — контракт, а не файл. Ниже — обязательная схема; форма хранения
(YAML, база, StrictDoc) остаётся решением реализации.

```yaml
core:
  id: CORE-2026-0042            # стабильный идентификатор ядра
  version: 3                     # растёт при любом изменении элемента
  route_ref: RK-2026-0042        # ссылка на маршрутный лист C-RK (из M4)
  input_ref: IA-2026-0117        # ссылка на верифицированный вход C-IA (из M0)
  scope:
    in: [<scope_tag>, ...]       # объявленный объём; основание INV-6
    out: [<scope_tag>, ...]      # явно исключённое — не менее ценно, чем включённое
  elements:
    - id: CORE-0042-EL-014
      type: EL-2                 # таксономия B файла 20-taxonomy.md
      statement: "..."
      source: {kind: ia-fragment, ref: "IA-2026-0117#p14"}
      verification: {kind: acceptance, ref: CORE-0042-EL-088}
      links: {up: [CORE-0042-EL-003], down: []}
      scope_tag: billing
      approval_status: AS-3
      version: 2
      change_reason: "уточнён предел по итогу HG-3"
      conflicts_with: []
  models:
    - {id: MO-3-01, class: MO-3, answers: U-3, covers: [CORE-0042-EL-014]}
  open_questions:
    - {id: CORE-0042-EL-091, type: EL-7, owner: "...", due: 2026-09-05}
  gate:
    hg4:
      passed_at: 2026-08-30
      owner_role: head-of-direction   # определяется осью A6, см. §3
      evidence_ref: "..."
```

### 1.1 Условия приёмки контракта (машинные)

| № | Условие | Инвариант |
| --- | --- | --- |
| `CC-1` | все `elements[].id` уникальны и стабильны между версиями | `INV-1` |
| `CC-2` | у каждого элемента непустой `source` | `INV-3` |
| `CC-3` | у каждого `EL-2`/`EL-4` есть `verification` либо `verification.kind = deferred` | `INV-4` |
| `CC-4` | каждый `scope.in` покрыт ≥ 1 элементом | `INV-6` |
| `CC-5` | нет висячих `links.up`/`links.down` | `INV-7` |
| `CC-6` | изменение элемента влечёт рост `version` и непустой `change_reason` | `INV-8` |
| `CC-7` | для передачи в `M2` все элементы имеют `approval_status ∈ {AS-3, AS-4}` | `INV-9`, `M1-R5` |
| `CC-8` | каждая модель ссылается на тип неопределённости `answers` | `M1-R3` |
| `CC-9` | `open_questions` пуст либо каждый вопрос имеет владельца и срок | — |

**Правило версионирования `M1-R6`.** `C-CORE` версионируется целиком, элементы
— по отдельности. Потребитель (`M2`) фиксирует пару `(core.id, core.version)`;
изменение версии ядра после сборки документа делает документ устаревшим
автоматически, а не по замечанию человека. Это техническая опора инварианта
`K5` RFC.

## 2. Применение осей `A1`–`A6` к `M1`

| Ось | Что меняет в `M1` | Что **не** меняет |
| --- | --- | --- |
| `A1` — набор целевых артефактов | требуемую полноту ядра: каждый артефакт набора предъявляет свой минимум типов `EL-*` (см. §2.1) | схему `C-CORE` |
| `A2` — бизнес-контекст | приоритет классов моделей: `tender-rfp` → `MO-12`, `MO-8`; `internal-product` → `MO-1`, `MO-2` | инварианты |
| `A3` — строгость `L1`/`L2`/`L3` | обязательный состав моделей (`M1-R1`) и глубину `verification` | набор инвариантов |
| `A4` — режим исполнения | число гейтов внутри `M1` и размер шага, а не результат | `C-CORE` |
| `A5` — глубина исследовательского потока | сколько сценарных моделей (`MO-3`) строится как стресс-тест и сохраняются ли они в ядре | обязательность `MO-3` при `L1` |
| `A6` — контур согласования | владельца `HG-4`, границу `T2` (сколько проектных решений попадает в ядро), обязательность `AS-4` | гранулярность |

### 2.1 Минимум ядра под элемент набора `A1`

| Элемент `A1` | Обязательные типы элементов | Обязательные модели |
| --- | --- | --- |
| `fr` | `EL-1`, `EL-2`, `EL-6`, `EL-8` | `MO-1`, `MO-3` |
| `tz` | `EL-1`…`EL-6`, `EL-8` | `MO-1`, `MO-2`, `MO-4`, `MO-7`, `MO-8`, `MO-12` |
| `us` | `EL-2`, `EL-8` | `MO-3` |
| `uc` | `EL-2`, `EL-5`, `EL-8` | `MO-3`, `MO-5` |
| `spec` | `EL-2`, `EL-3`, `EL-4`, `EL-8` | `MO-4`, `MO-7`, `MO-8` |
| `bcreq` | `EL-1`, `EL-2`, `EL-3`, `EL-7` | `MO-1`, `MO-12` |
| `custom-form` | определяется формой заказчика | `MO-12` обязателен |

**Правило `M1-R7` (объединение, а не пересечение).** При наборе из нескольких
артефактов минимум ядра — **объединение** их минимумов. Обратное правило
(пересечение) выглядит экономнее, но гарантированно ломает `K5`: часть
документов пришлось бы дописывать вне ядра.

**Правило `M1-R8` (`custom-form` не понижает уровень).** Навязанная форма
заказчика задаёт разметку выхода, но не отменяет требований `A3`. Если в форме
нет места для критериев приёмки, критерии остаются в ядре и выдаются
приложением — вопрос `RQ-2.8` в `M2`.

## 3. Гейты `M1`: `HG-0`, `HG-2`, `HG-3`, `HG-4`

`HG-1` относится к `M0` (полнота нормализованного входа) и здесь не
переопределяется.

| Гейт | Событие | Владелец | Машинно-проверяемое предусловие |
| --- | --- | --- | --- |
| `HG-0` | подтверждение маршрутного листа до первой генерации | владелец процесса | `C-RK` существует, все шесть осей заданы, ключ маршрута непротиворечив по `C1`–`C6` |
| `HG-2` | закрытие критичных пробелов: вопросы заказчику отправлены и получены ответы либо приняты предположения | БА | каждый `EL-7` имеет владельца и срок; ни один `EL-7` со статусом `blocking` не остался без решения |
| `HG-3` | приёмка моделей: построенные модели покрывают заявленные типы неопределённости | БА + профильный эксперт | для каждого `U-*`, объявленного в маршруте, есть модель с `answers = U-*`; каждая модель покрывает ≥ 1 элемент ядра |
| `HG-4` | согласование ядра с владельцем | зависит от `A6` (см. ниже) | все элементы в `AS-3`/`AS-4`; `CC-1`…`CC-9` выполнены; расхождений с `C-IA` по `INV-3` нет |

### 3.1 Владелец `HG-4` — ответ на `Q-4` RFC

Принят вариант «в»: **владелец определяется осью `A6`**.

| `A6` | Владелец `HG-4` | Обоснование через необратимость |
| --- | --- | --- |
| `internal` | БА | ошибка исправляется следующей итерацией; цена низкая |
| `external-contract` | руководитель направления | согласованное ядро становится основанием договорных обязательств; цена ошибки — деньги и сроки |
| `regulated` | руководитель направления + профильный контроль (юрист/безопасность) | цена ошибки включает регуляторные последствия, которые БА не уполномочен принимать |

Аргумент против фиксированного владельца: закрепление гейта за БА делает
подпись формальной в договорном контуре; закрепление за руководителем делает
её узким местом во внутреннем. Ось `A6` уже описывает ровно то различие, от
которого зависит цена ошибки, поэтому вводить седьмую ось не требуется.

### 3.2 Почему `HG-4` необратим

Правило `F5` RFC (необратимость) в `M1` означает: после `HG-4` элементы
переходят в `AS-4` и изменяются только через процедуру изменений с новой
версией ядра. Практическое следствие: **`M2` никогда не собирает документ из
ядра, которое ещё может измениться молча** — иначе недрейф недоказуем.

## 4. Правила выбора моделей (алгоритм)

```text
1. Из C-RK взять A1, A3, A5.
2. Обязательный состав моделей := M1-R1(A3) ∪ (по каждому элементу A1: §2.1).
3. Из материала C-IA разметить типы неопределённости U-1..U-7.
4. Для каждого размеченного U-* добавить соответствующий класс модели.
5. Если A5 >= us: добавить MO-3 как стресс-тест даже при отсутствии U-3.
6. Если A5 = us+uc+competitive: добавить MO-11 (варианты решения).
7. Модель без ссылки на U-* или без покрытых элементов не строится (M1-R3).
8. HG-3 проверяет пункты 2-7 машинно.
```

Пункт 5 фиксирует правило `F2` RFC: US/UC при `A1 ∉ {us, uc}` строятся **как
инструмент**, их результат — найденные пробелы, попадающие в ядро элементами,
а не как выход конвейера.

## 5. Правило разрешения конфликтов в ядре

`INV-5` требует, чтобы конфликты были помечены, но не говорит, как их
разрешать. Предлагается порядок приоритета `M1-R9`:

1. Регуляторное ограничение (`EL-3` с `source.kind = regulation`).
2. Договорное обязательство (`EL-3` с `source.kind = contract`).
3. Явное решение владельца `HG-4`, зафиксированное как `change_reason`.
4. Бизнес-правило (`EL-5`) с более узкой областью действия.
5. Функциональное утверждение более позднего источника.

Если порядок не разрешает конфликт, элементы остаются `AS-2` и блокируют
`HG-4`. Тихое разрешение конфликта аналитиком запрещено: это `D-4`,
превращающийся в `D-8`.

## 6. Build-vs-buy screening

Скрининг по правилу RFC «не изобретать велосипед». Оценивается покрытие
**инвариантов**, а не удобство.

| Кандидат | Что закрывает | Чего не закрывает | Вердикт скрининга |
| --- | --- | --- | --- |
| [StrictDoc](https://github.com/strictdoc-project/strictdoc) | `INV-1`, `INV-4`, `INV-7`, `INV-8`; текстовые требования как код, экспорт в документы | `INV-9` на уровне элемента (статусы есть, но контур согласования свой), связь с моделями `MO-*` | **кандидат №1 на пилот** для `C-CORE` |
| [Doorstop](https://github.com/doorstop-dev/doorstop) | `INV-1`, `INV-7`, `INV-8`; git-native, минимальная схема | публикация под аудитории, богатые атрибуты | кандидат на минимальный контур `L1` |
| [Sphinx-Needs](https://github.com/useblocks/sphinx-needs) | `INV-1`, `INV-7`; фильтрация и проекции под аудитории (`M1-R4`) | версионирование элемента, статусы согласования | кандидат для проекций, не для хранения |
| ReqIF / OSLC | межорганизационный обмен ядром; сохранение идентификаторов | внутреннюю работу и модели | принять как **формат обмена**, не как хранилище |
| DMN (в т. ч. Camunda) | `MO-6` целиком: правила как исполняемая таблица решений | остальные классы | принять для `EL-5`/`MO-6` при `L2`+ |
| BPMN-редакторы (bpmn.io) | `MO-2`, частично `MO-7` | связь диаграммы с элементами ядра | принять как нотацию, связь строить самим |
| Классические RM-платформы (Jama, Polarion, DOORS) | почти все инварианты | стоимость, закрытость, несовместимость с git-контуром Хаба | вне рамки: архетип репозиториев требует открытого текстового контура |

**Что остаётся собственной разработке (`RQ-1.7`).** Три вещи, не закрытые ни
одним кандидатом: (1) связь `модель ↔ элемент ядра ↔ тип неопределённости`
(`M1-R3`, `CC-8`); (2) проекции под аудитории `AUD-1`…`AUD-5` как правило, а не
как ручная выборка (`M1-R4`); (3) гейтовая механика `AS-*` с владельцем по
`A6`. Всё остальное следует брать готовым.
