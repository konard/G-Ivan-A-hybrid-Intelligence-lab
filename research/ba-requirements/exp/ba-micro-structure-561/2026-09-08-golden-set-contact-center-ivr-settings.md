# Golden Set `GS-CC-01`: `contact-center`, функция с настройками

> **Синтетический эталон.** Документ ниже никому не поставлялся. Он собран как
> модель ожидаемой структуры по правилам
> [модуля](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/blob/main/research/ba-requirements/artifact-micro-structure/20-taxonomy.md),
> потому что корпус `runs/` не даёт чистой выборки этого продуктового класса
> (§6 [замера](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/blob/main/research/ba-requirements/2026-09-08-artifact-structure-variance-facts.md)).
> Данные вымышлены; идентификатор `BCREQ-9001` и ссылки на базу знаний —
> заглушки формы, а не факты.

**Продуктовый класс:** `contact-center` → capability «Маршрутизация обращений»
→ feature «Очередь и приоритеты» → atomic function «Переполнение очереди».
**Профиль:** `P-SETTINGS` — у функции есть пользовательская настройка,
поэтому слоты `S-SETTINGS` и `S-UI` обязательны.
**Формат:** `F-CLASSIC`.
**Назначение эталона:** few-shot образец и структурный образец гейта `G-mach`.

## 1. Термины и определения

| Термин | Определение | Источник |
| --- | --- | --- |
| Очередь | Упорядоченный набор обращений, ожидающих свободного оператора группы. | KB: `queues/overview` |
| Порог переполнения | Настраиваемая длина очереди, при достижении которой включается альтернативный сценарий. | новое понятие настоящего документа |
| Альтернативный сценарий | Действие с обращением при достижении порога: обратный звонок, голосовая почта, перевод в другую группу. | KB: `queues/overflow` |

## 2. Проблема, цель, границы изменения

**Проблема.** При пиковой нагрузке обращение остаётся в очереди неограниченно
долго; администратор группы не может задать поведение системы для этого случая.

**Цель.** Дать администратору настройку порога переполнения и выбор
альтернативного сценария на уровне группы.

**Границы.** В объёме — очереди голосового канала. Вне объёма — очереди чатов
и e-mail; их поведение настоящим документом не меняется.

## 3. Текущее состояние и требуемая дельта

| # | Наблюдаемое текущее состояние | Источник факта | Требуемая дельта |
| --- | --- | --- | --- |
| 3.1 | Длина очереди не ограничена, обращение ждёт до ответа или отбоя. | KB: `queues/overview`, раздел 4 | Ввести порог и действие при его достижении. |
| 3.2 | В карточке группы 6 настроек, блока «Очередь» нет. | UI администратора, экран «Группы» | Добавить блок «Очередь» с двумя полями. |
| 3.3 | Событие «обращение покинуло очередь по таймауту» в отчётах отсутствует. | KB: `reports/queue-events` | Добавить событие с причиной. |

## 4. Функциональные требования (системная логика)

| ID | Требование | Дельта из §3 |
| --- | --- | --- |
| ФТ-4.1 | Система вычисляет длину очереди группы при каждом изменении её состава. | 3.1 |
| ФТ-4.1.1 | Если длина очереди ≥ порога, к новому обращению применяется альтернативный сценарий группы. | 3.1 |
| ФТ-4.1.2 | Если порог не задан, поведение очереди не изменяется. | 3.1 |
| ФТ-4.2 | Система сохраняет событие выхода из очереди с причиной `overflow` и значением порога на момент события. | 3.3 |
| ФТ-4.2.1 | Событие доступно в отчёте «События очереди» не позднее 60 секунд после наступления. | 3.3 |

## 5. Настройки

| ID | Настройка | Область | Значения | По умолчанию |
| --- | --- | --- | --- | --- |
| Н-5.1 | Порог переполнения | группа | пусто или целое 1…999 | пусто (поведение не меняется) |
| Н-5.2 | Альтернативный сценарий | группа | обратный звонок, голосовая почта, перевод в группу | обратный звонок |

Правило совместимости: `Н-5.2` применяется только при непустом `Н-5.1`.

## 6. UI-логика

| ID | Элемент | Поведение |
| --- | --- | --- |
| UI-6.1 | Блок «Очередь» в карточке группы | Отображается ролям с правом редактирования группы. |
| UI-6.2 | Поле «Порог переполнения» | Пустое значение допустимо. Нечисловой ввод блокируется на вводе. |
| UI-6.3 | Список «Альтернативный сценарий» | Неактивен при пустом `Н-5.1`, подсказка объясняет причину. |
| UI-6.4 | Сохранение | При значении вне диапазона 1…999 форма не сохраняется, ошибка показывается у поля. |

> Раздел отделён от §4 намеренно. Замер показал `S-UI` = 1 раздел на 17
> документов: поведение интерфейса растворяется внутри функциональных
> требований, из-за чего согласование с заказчиком и разработка читают один
> текст по-разному.

## 7. Сценарии использования

| ID | Сценарий | Шаги | Ожидаемый результат |
| --- | --- | --- | --- |
| СЦ-7.1 | Порог достигнут, выбран обратный звонок | 1) очередь = порогу; 2) поступает обращение | Абоненту предложен обратный звонок, событие `overflow` записано |
| СЦ-7.2 | Порог не задан | 1) очередь растёт | Поведение прежнее, событий `overflow` нет |
| СЦ-7.3 | Порог изменён при непустой очереди | 1) администратор снижает порог | Правило применяется к новым обращениям, очередь не пересобирается |
