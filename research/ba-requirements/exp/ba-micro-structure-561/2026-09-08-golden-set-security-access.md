# Golden Set `GS-SEC-01`: `security`, ограничение доступа

> **Синтетический эталон повышенного риска.** Документ никому не поставлялся,
> данные вымышлены. Документов домена `security` в доступных данных нет;
> основание синтеза — правила профиля `P-SETTINGS` и индустриальная практика
> описания управления доступом. Пороговые значения условны и подлежат
> подтверждению владельцем домена.

**Продуктовый класс:** `security` → capability «Управление доступом» → feature
«Ограничение по адресу подключения» → atomic function «Разрешение входа с
доверенных адресов».
**Профиль:** `P-SETTINGS` — поведение управляется администратором клиента.
**Формат:** `F-CLASSIC`.
**Назначение эталона:** показать, что домен, чья специфика — запреты и риски,
укладывается в тот же скелет: специфика домена целиком садится в `S-LIMITS` и
`S-AC`, а не требует раздела «Безопасность».

## 1. Термины и определения

| Термин | Определение | Источник |
| --- | --- | --- |
| Доверенный адрес | Сетевой адрес или диапазон, с которого вход разрешён. | новое понятие настоящего документа |
| Список доступа | Перечень доверенных адресов аккаунта. | новое понятие настоящего документа |
| Аварийный доступ | Вход владельца аккаунта при пустом или ошибочном списке. | новое понятие настоящего документа |

## 2. Проблема, цель, границы изменения

**Проблема.** Учётная запись администратора доступна из любой сети: компрометация
пароля даёт полный доступ к телефонии клиента.

**Цель.** Дать администратору клиента ограничить вход адресами его организации.

**Границы.** В объёме — ограничение входа в панель управления. Вне объёма —
ограничение регистрации абонентских устройств, второй фактор аутентификации,
парольная политика.

## 3. Текущее состояние и требуемая дельта

| # | Текущее состояние | Источник факта | Требуемая дельта |
| --- | --- | --- | --- |
| 3.1 | Вход разрешён с любого адреса при верных данных. | поведение панели управления | Проверять адрес по списку доступа. |
| 3.2 | Списка доступа не существует. | отсутствует | Ввести список на уровне аккаунта. |
| 3.3 | Отказы входа не разделяются по причине. | журнал входов | Различать отказ по данным и отказ по адресу. |

## 4. Функциональные требования (системная логика)

| ID | Требование | Дельта из §3 |
| --- | --- | --- |
| ФТ-4.1 | При непустом списке доступа система разрешает вход только с адреса из списка. | 3.1, 3.2 |
| ФТ-4.2 | При пустом списке доступа ограничение не применяется. | 3.2 |
| ФТ-4.3 | Система фиксирует в журнале отказ по адресу отдельным признаком. | 3.3 |
| ФТ-4.4 | Система предоставляет владельцу аккаунта аварийный доступ по подтверждению из независимого канала. | 3.2 |
| ФТ-4.5 | Система уведомляет владельца аккаунта о каждом изменении списка доступа. | 3.2 |

## 5. Описание решения

Список доступа на уровне аккаунта, проверка адреса выполняется после проверки
учётных данных и до создания сессии. Порядок проверок существен: он определяет,
что видит атакующий (§9).

## 6. Настройки

| ID | Настройка | Значение по умолчанию | Кто изменяет |
| --- | --- | --- | --- |
| Н-6.1 | Список доверенных адресов | пуст | администратор аккаунта |
| Н-6.2 | Уведомление владельца об изменении списка | включено | не изменяется |

## 7. UI-логика

| ID | Элемент | Поведение |
| --- | --- | --- |
| UI-7.1 | Раздел «Доступ», список адресов | Показывает адреса, позволяет добавить и удалить. |
| UI-7.2 | Добавление адреса | Текущий адрес администратора предложен значением по умолчанию. |
| UI-7.3 | Сохранение списка без текущего адреса | Показывает предупреждение о потере доступа и требует подтверждения. |
| UI-7.4 | Экран отказа входа | Сообщение одинаково для отказа по данным и по адресу. |

`UI-7.4` — место, где домен меняет обычное правило: пользователю **не**
сообщается действительная причина отказа, потому что различимость причин
является уязвимостью. Требование к журналу (`ФТ-4.3`) и требование к экрану
поэтому расходятся намеренно, и расхождение зафиксировано в критерии `КП-9.3`.

## 8. Сценарии использования

| ID | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| СЦ-8.1 | Вход с адреса из списка. | Сессия создана. |
| СЦ-8.2 | Вход с адреса вне списка при верном пароле. | Отказ, в журнале — отказ по адресу. |
| СЦ-8.3 | Вход с адреса из списка при неверном пароле. | Отказ, в журнале — отказ по данным, сообщение то же, что в СЦ-8.2. |
| СЦ-8.4 | Администратор удалил из списка собственный адрес и подтвердил. | Текущая сессия завершена, повторный вход невозможен, доступен аварийный доступ. |
| СЦ-8.5 | Владелец использует аварийный доступ. | Доступ предоставлен после подтверждения, событие зафиксировано и отправлено владельцу. |

## 9. Критерии приёмки

| ID | Требование | Критерий | Способ проверки |
| --- | --- | --- | --- |
| КП-9.1 | ФТ-4.1 | Вход с адреса вне списка не создаёт сессию ни при одной из 100 попыток. | тест |
| КП-9.2 | ФТ-4.2 | При пустом списке вход с произвольного адреса успешен. | тест |
| КП-9.3 | ФТ-4.3, UI-7.4 | Ответы системы в СЦ-8.2 и СЦ-8.3 неразличимы по содержанию, коду и времени ответа; в журнале причины различны. | тест |
| КП-9.4 | ФТ-4.4 | Аварийный доступ невозможен без подтверждения из независимого канала. | приёмка |
| КП-9.5 | ФТ-4.5 | Каждое изменение списка порождает ровно одно уведомление владельцу. | машинная |

## 11. Ограничения

| ID | Ограничение |
| --- | --- |
| ОГР-11.1 | Ограничение действует только для входа в панель управления. |
| ОГР-11.2 | Клиенты с динамическим адресом вынуждены указывать диапазон, что снижает эффект меры; альтернатива вне объёма. |
| ОГР-11.3 | Мера не защищает от доступа из доверенной сети, то есть не заменяет второй фактор. |

`ОГР-11.3` — граница применимости самой меры. В домене `security` она
обязательна: требование без границы применимости создаёт ложное представление
о защищённости.
