## 1. Матрица корреляции: универсальная ↔ Mango-таксономия

`[U]`+`[M]` Матрица отвечает на вопрос «что из универсального у Mango уже есть,
что есть под другим именем, а чего нет». Столбец «дельта» — единственный
источник работ для переписывания процессов; всё остальное трогать не нужно.

| Универсальный процесс | Mango: где живёт сейчас | Соответствие | Дельта |
| --- | --- | --- | --- |
| U1 Регистрация | `runs/` (пост-фактум) + issue-трекер | **частичное** | регистрируется прогон, а не обращение; исходный IA не имеет идентификатора |
| U2 Классификация | выбор процесса по [`docs/ba-processes/00-index.md`](https://github.com/G-Ivan-A/mango_ba_prompts/blob/main/docs/ba-processes/00-index.md) | **частичное** | классифицируется маршрут, а не артефакт; классов IA нет |
| U3 Оценка покрытия | внутри анализа ФТ, неявно | **отсутствует как процесс** | нет операции с собственным выходом и гейтом; нет различения «нет функции» / «скрытое покрытие» |
| U4 Уточнение | состояние `needs-clarification` | **полное** | нет правила пакетирования вопросов для внешнего контура |
| U5 Нормализация формы | 13 когнитивных операций, 24 промпта | **полное** | изменений не требуется |
| U6 Анализ влияния | процессы работы с ТЗ и ФТ | **частичное** | baseline фиксируется не для всех типов артефактов |
| U7 Выбор модели решения | отсутствует | **отсутствует** | решение «продукт/кастом» принимается вне процесса и не записывается |
| U8 Верификация | правила С1–С8, гейты `validated/approved/baselined` | **полное** | гейт человеческий и, по H4, ненадёжный сам по себе |
| U9 Статистика | `runs/` + `metadata.yaml` | **частичное** | схема метрик не зафиксирована; учитываются прогоны, а не требования |

Сцепка предметных областей идёт по цепочке классификации продукта
`domain → capability → feature → atomic function`
([контракт Mango](https://github.com/G-Ivan-A/mango_ba_prompts/blob/main/standards/product-classification-contract.md)):

| Универсальное понятие | Уровень цепочки | Что на нём решается |
| --- | --- | --- |
| O5 покрытие | `feature` / `function` | есть ли реализация |
| IA-3 Demand Item | `capability` | нужна ли новая возможность |
| IA-5 Discovery Query | `function` | доступна ли функция этому источнику |
| U7 модель решения | `capability` ↔ `feature` | продуктовое расширение или точечная доработка |

**Вывод.** Совпадение полное там, где работа идёт **внутри** артефакта (U5, U8),
и отсутствует там, где работа идёт **на границе** процесса (U3, U7, U9). Это
согласуется с тезисом
[`10-theory.md` §2](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/blob/main/research/ba-requirements/normalization/10-theory.md#2-объектная-модель):
переписывать нужно компоновку и гейты, а не операции.

## 2. Цикл нормализации и гейты

`[U]` Семь шагов N1–N7 и шесть гейтов G1–G6. Гейт — это место, где процесс
**обязан остановиться**, если условие не выполнено; «остановиться» означает
вернуться к источнику или зафиксировать отказ, но не «продолжить с допущением».

```text
N1 фиксация ──G1──> N2 классификация ──G2──> N3 разбор смысла
     └──> N4 оценка покрытия ──G3──> N5 уточнение ──G4──> N6 нормализация
                                          │                    │
                                          └────не закрыт───────┘
                                                               ▼
                                              N7 решение ──G5──> учёт ──G6──> baseline
```

| Шаг | Содержание | Гейт | Условие прохождения | Владелец гейта | Действие при непрохождении |
| --- | --- | --- | --- | --- | --- |
| N1 | зафиксировать обращение как есть, с источником и датой | G1 | источник идентифицирован, текст сохранён дословно | S-I5 / S-I4 | не регистрировать пересказ вместо оригинала |
| N2 | присвоить класс IA и значения осей O1–O6 | G2 | класс единственный; при двух классах артефакт расщеплён | S-I4 | расщепление или возврат на уточнение |
| N3 | разобрать формулировку по словам и связкам, выделить неоднозначные термины | — | — | S-I4 | — |
| N4 | сопоставить с контекстом продукта; присвоить O5 | G3 | указан конкретный `feature`/`function` либо явно зафиксировано «не найдено» с перечнем проверенного | S-I4 + S-I1 | запрет перехода к N6 |
| N5 | сформировать **пакет** уточняющих вопросов по `Residual` | G4 | `Residual` пуст либо явно принят как допущение с подписью источника | S-I4 + источник | возврат к источнику; для внешнего контура — один пакет, не поток |
| N6 | сформулировать требование с проверяемым критерием | — | 9 характеристик ISO/IEC/IEEE 29148 | S-I4 | — |
| N7 | выбрать модель решения (§3) | G5 | выбор записан с обоснованием и альтернативами | S-I1 или коммерческая функция | решение не считается принятым |
| — | учесть исход в реестре | G6 | запись реестра закрыта любым из статусов, включая «отклонено» | владелец реестра | процесс не завершён |

### 2.1 Что именно нового в этих гейтах

- **G3 — новый гейт.** Раньше оценка покрытия была подшагом без выхода; теперь
  это точка остановки. Прямое следствие наблюдения «покрыт* — 41 прогон из 56».
- **G4 требует не «вопросы заданы», а «`Residual` закрыт или принят».** Разница
  принципиальна: в RUN-0023 вопросы **были заданы** (7 штук) и остались без
  ответа, а работа продолжилась.
- **G6 закрывает процесс на реестре, а не на артефакте.** Отклонённое обращение
  тоже должно быть учтено, иначе статистика описывает только успехи.

### 2.2 Проверяемость гейтов

`[U]` По гипотезе H4 человеческая подпись не является достаточным критерием.
Поэтому для каждого гейта указан машинно-проверяемый минимум:

| Гейт | Машинно-проверяемый минимум |
| --- | --- |
| G1 | наличие непустого поля «источник» и дословного текста |
| G2 | класс из перечисления IA-1…IA-7; все шесть осей заполнены |
| G3 | ссылка на элемент продуктовой модели **или** явная отметка «не найдено» + список проверенного |
| G4 | список `Residual` пуст или каждый элемент помечен `answered` / `assumed` |
| G5 | значение из перечисления моделей решения + непустое обоснование |
| G6 | статус записи реестра из перечисления |

Ни один из этих критериев не проверяет **истинность** — они проверяют, что шаг
не был пропущен молча. Это меньше, чем хотелось бы, и больше, чем есть сейчас.

## 3. Выбор модели решения

`[U]` Вход: значение O5 (покрытие), O3 (массовость), O4 (коммерческая рамка),
O6 (обязательность). Выход: одно из пяти решений.

| Код | Решение | Когда |
| --- | --- | --- |
| D-A | **Ответ без разработки** | O5 = полное; функция доступна источнику |
| D-B | **Снятие барьера доступа** | O5 = скрытое покрытие: функция есть, закрыта тарифом или ролью |
| D-C | **Конфигурация** | O5 = частичное, потребность закрывается настройкой без изменения кода |
| D-D | **Продуктовое изменение** | O5 = частичное/отсутствует и O3 ≠ единичное |
| D-E | **Кастом по договору** | O5 = отсутствует, O3 = единичное, O4 = платный кастом |
| D-F | **Отказ** | O6 = дискреционное и ценность не обоснована |

Матрица решения:

| O5 \ O3 | единичное | повторяющееся | массовое |
| --- | --- | --- | --- |
| **полное** | D-A | D-A + сигнал в U9 (проблема discoverability) | D-A + продуктовая работа над обнаружимостью |
| **скрытое покрытие** | D-B | D-B + пересмотр упаковки тарифа | D-B + продуктовое решение по упаковке |
| **частичное** | D-C, при отказе → D-E | D-C или D-D | D-D |
| **отсутствует** | D-E или D-F | D-D | D-D, приоритет вне очереди |

Три правила, ограничивающие матрицу:

1. **`O6 = обязательное` отменяет D-F** — регуляторное требование не может быть
   отклонено по ценности.
2. **Полный кастом — нежелательный по умолчанию исход (гипотеза H8).** Он
   допустим при O3 = единичное и O4 = платный кастом, и требует явного
   признания стоимости владения: отдельная ветка сопровождения, отдельная
   регрессия, отдельная документация.
3. **Массовое обращение при полном покрытии — это не продуктовая задача о
   функции, а продуктовая задача об обнаружимости.** Верхняя правая ячейка —
   самая часто ошибочно интерпретируемая: команда начинает разрабатывать то,
   что уже есть.

## 4. Три гипотезы реализации

`[U]`+`[M]` Гипотезы заданы в issue
[#539](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/issues/539).
Оцениваются по одинаковым критериям; ни одна не отбрасывается без причины.

### 4.1 H-M — ручная реализация

Пошаговая библиотека промптов + инструкции; человек ведёт процесс, вызывая
операции по одной.

| Аспект | Оценка |
| --- | --- |
| Что требуется от таксономии | классы IA и оси как **чек-лист** в тексте инструкции |
| Что требуется от артефактов | шаблон записи IA; отдельного хранилища не нужно |
| Что требуется от библиотеки промптов | один промпт на операцию; порядок задаёт человек |
| Сильная сторона | гейты выполняются осознанно; ошибка ловится на шаге |
| `[M]` Эмпирика | режим `stepwise` уже существует; медиана 15 эпизодов и 44 реплик на прогон |
| Слабая сторона | не масштабируется: медианный прогон — 720 806 токенов диалога и 19 итераций; при 56+ обращениях стоимость линейна по числу обращений |
| Риск | пропуск шага не обнаружим: нет машинной проверки G1–G6 |

### 4.2 H-A — автоматическая реализация

Один промпт на операцию (one-shot) + гейты, исполняемые AI-агентом.

| Аспект | Оценка |
| --- | --- |
| Что требуется от таксономии | классы и оси как **перечисления в схеме данных**, а не как текст |
| Что требуется от артефактов | машинночитаемая запись IA (структурированный формат) и реестр |
| Что требуется от библиотеки промптов | по одному самодостаточному промпту на операцию + контракт входа/выхода |
| Сильная сторона | шаг нельзя пропустить молча: G1–G6 проверяются по §2.2 |
| `[M]` Эмпирика | режим `oneshot` уже существует |
| Слабая сторона | заземление: при 9 прогонах с `hallucinations_shipped > 0` автоматический маршрут без верификации переносит вымысел дальше и быстрее |
| Риск | стоимость переносится с генерации на верификацию (гипотеза H10), а не исчезает |

### 4.3 H-H — гибрид

Репозиторий Mango как хранилище знаний и контрактов + AI-агент, исполняющий
прогоны по задачам; человек владеет гейтами G3, G5 и выборочно G4.

| Аспект | Оценка |
| --- | --- |
| Что требуется от таксономии | двойное представление: человекочитаемое (документ) и машинное (перечисления) — из одного источника |
| Что требуется от артефактов | реестр IA в репозитории; `runs/` остаётся операционным журналом |
| Что требуется от библиотеки промптов | оба режима: `oneshot` для операций с проверяемым выходом, `stepwise` для операций, где нужен диалог с источником |
| Сильная сторона | человек стоит там, где машинная проверка невозможна (истинность покрытия, коммерческое решение), а машина — там, где невозможна дисциплина (полнота шагов, учёт) |
| `[M]` Эмпирика | оба режима уже реализованы в спице; 47 из 56 прогонов заведены как `statistics`, то есть инфраструктура учёта существует |
| Слабая сторона | два маршрута = двойная стоимость сопровождения контрактов |
| Риск | размывание ответственности на гейтах, если владелец каждого гейта не назначен поимённо |

### 4.4 Сравнение и рекомендация

| Критерий | H-M | H-A | H-H |
| --- | --- | --- | --- |
| Масштабируемость | низкая | высокая | высокая |
| Проверяемость прохождения гейтов | низкая | высокая | высокая |
| Устойчивость к вымыслу | средняя | **низкая** | средняя–высокая |
| Стоимость внедрения | низкая | средняя | высокая |
| Стоимость сопровождения | высокая (на обращение) | низкая | средняя |
| Готовность инфраструктуры Mango | есть | есть | есть |

**Рекомендация: H-H.** H-M отпадает по масштабируемости, H-A — по
устойчивости к вымыслу при текущей эмпирике (H4). H-H выбирается не как
компромисс, а по правилу распределения: **машина исполняет то, что проверяемо
формально; человек — то, что проверяемо только по существу.** Рекомендация
подлежит пересмотру, если H4 будет опровергнута.

## 5. Процесс статистики и реестр требований

`[U]` Процесс U9. Отделён от решения о включении в продукт: у них разные
владельцы, разные сроки и разные критерии.

| Вопрос | Ответ |
| --- | --- |
| **Что учитывается** | каждый инициирующий артефакт, включая отклонённые, дубли и IA-5, закрытые ответом без разработки |
| **Кто ведёт** | владелец реестра (S-I4 по умолчанию); регистрируют — все, кто принимает обращения (S-I5) |
| **Когда** | запись создаётся в N1 (в момент фиксации), закрывается на G6; агрегаты снимаются на фиксированном ритме |
| **Как реализовано** | `[M]` в гибридной модели — структурированный реестр в репозитории спицы, агрегация скриптом, снимок с датой и SHA источника |

### 5.1 Схема записи реестра

| Поле | Назначение | Обязательно |
| --- | --- | --- |
| `id` | идентификатор IA | да |
| `received_at`, `source`, `stakeholder_code` | происхождение | да |
| `raw_text_ref` | ссылка на дословный оригинал | да |
| `ia_class` | IA-1…IA-7 | да, после N2 |
| `axes` | O1–O6 | да, после N2 |
| `coverage` | O5 + ссылка на элемент продуктовой модели | да, после G3 |
| `residual_status` | `open` / `answered` / `assumed` | да |
| `decision` | D-A…D-F + обоснование | да, после G5 |
| `outcome_status` | `accepted` / `deferred` / `rejected` / `duplicate` | да, на G6 |
| `duplicate_of` | сцепка для подсчёта массовости O3 | если применимо |
| `cost_signals` | итерации, токены, календарные дни | по возможности |

Поле `duplicate_of` — не бухгалтерия: именно оно превращает поток единичных
обращений в измеримую массовость (O3) и питает переход D-C → D-D.

### 5.2 Чем реестр **не** является

Реестр не является бэклогом и не выражает намерения делать. Смешение этих
сущностей — причина, по которой статистика обычно описывает только принятые
требования: отклонённое не попадает в бэклог и потому исчезает из статистики.
`[M]` Текущий `runs/` учитывает **прогоны**, а не обращения; это не дефект
`runs/`, это другой объект учёта.

### 5.3 Минимальный набор агрегатов

| Агрегат | Зачем |
| --- | --- |
| распределение IA по классам и осям | проверка того, что таксономия описывает реальный поток (вход §7) |
| доля IA, закрытых D-A/D-B | измерение проблемы обнаружимости |
| доля IA с `residual_status = assumed` на момент G6 | прямой прокси риска домысливания |
| доля IA, дошедших до `approved` и затем отменённых | проверка гипотезы H6 (§4.2 файла `20-taxonomy.md`) |
| время от `received_at` до G5 по контурам | проверка гипотезы H2 |

### 5.4 Требование к схеме метрик

`[M]` Наблюдение из корпуса: галлюцинации записаны тремя ключами
(`hallucinations`, `hallucinations_found`, `hallucinations_prevented`), а
ранние прогоны держат метрики в блоке `eval:`, поздние — в `metrics:`. Отсюда
требование: **схема метрик фиксируется контрактом и валидируется машинно**,
иначе агрегаты не сопоставимы между периодами. Это относится и к реестру IA.

## 6. Основание для переписывания BA-процессов

`[U]`+`[M]` Что именно даёт право переписывать процессы — и что переписывать
нельзя.

**Не меняется на этой итерации:** 13 когнитивных операций, 30 типов артефактов,
8 состояний артефакта, правила С1–С8, содержание 24 действующих промптов.
Основание: в матрице §1 все процессы, работающие внутри артефакта (U5, U8),
имеют **полное** соответствие — дефекта нет, менять нечего.

**Переписывается:** компоновка операций, гейты и учёт. Основание по пунктам:

| # | Что переписывается | Основание | Доказательство |
| --- | --- | --- | --- |
| R1 | Ввести регистрацию обращения (U1) как отдельный шаг с идентификатором IA | учёт ведётся по прогонам, а не по обращениям | 32 из 56 прогонов начинаются с уже упакованного `task-` |
| R2 | Ввести классификацию артефакта (U2) с классами IA и осями | маршрут выбирается без типизации входа | нет класса IA-5 при 3 упоминаниях «уже реализован*» |
| R3 | Выделить оценку покрытия (U3) в операцию с гейтом G3 | процесс отсутствует, задача решается постоянно | «покрыт*» — 41 прогон из 56, `discoverab*` — 0 |
| R4 | Усилить гейт уточнения (G4) критерием закрытия `Residual` | заданные вопросы не равны полученным ответам | RUN-0023: 7 вопросов без ответа, работа продолжена |
| R5 | Ввести выбор модели решения (U7) как записываемое решение | решение принимается вне процесса | «кастом» — 10 прогонов, критериев нет |
| R6 | Ввести реестр и фиксированную схему метрик (U9) | метрики разнородны, отклонённое не учитывается | три ключа для галлюцинаций; `success_rate` несопоставим по признанию метаданных |
| R7 | Добавить машинно-проверяемый минимум к каждому гейту | человеческий гейт не удерживает вымысел (H4) | `hallucinations_shipped > 0` в 9 прогонах |

**Ограничение основания.** R1–R7 обоснованы корпусом, смещённым к поздним
стадиям (см. ограничения в
[`00-introduction.md` §5](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/blob/main/research/ba-requirements/normalization/00-introduction.md#5-ограничения-и-честные-пробелы)).
Наиболее уязвим R1: он выведен из отсутствия данных о раннем участке, а
отсутствие данных — слабее прямого наблюдения. Это зафиксировано как открытый
вопрос, а не скрыто.

## 7. Гейт эволюции таксономии

`[U]` Таксономия, которую нельзя изменить, через год описывает несуществующий
поток; таксономия, которую меняет любой участник, перестаёт быть общим языком.
Поэтому изменение проходит через явный гейт.

| Элемент | Правило |
| --- | --- |
| **Триггер** | накопление IA, не укладывающихся ни в один класс, выше порога; либо класс, не встретившийся ни разу за период; либо решение D-*, систематически принимаемое вопреки матрице §3 |
| **Кто инициирует** | владелец реестра на основании агрегатов §5.3 |
| **Что предъявляется** | перечень конкретных записей реестра, которые действующая таксономия описывает неверно |
| **Кто решает** | владелец продукта (S-I1) совместно с владельцем нормализации (S-I4) |
| **Как фиксируется** | версия таксономии повышается; изменение проходит RFC/ADR по правилам Хаба |
| **Что запрещено** | менять классы «по ощущению», без предъявления записей реестра |

Этот гейт замыкает контур обратной связи из
[`10-theory.md` §2.1](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/blob/main/research/ba-requirements/normalization/10-theory.md#21-граф-зависимостей):
реестр является **единственным** легитимным основанием для изменения
таксономии. Без этого правила гейт превращается в согласование мнений.
