# Теория: чем процесс отличается от списка работ

## 1. Что сломалось в унаследованной таксономии

Унаследованные девять процессов не образуют таксономии по трём независимым
причинам, каждая из которых измерена
([отчёт `D1`–`D8`](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/blob/main/research/ba-requirements/2026-09-10-process-taxonomy-defects-facts.md)).

| Причина | Что именно нарушено | Дефект |
| --- | --- | --- |
| Нет единственного выхода | `fr-generation` объявляет выходом `A-FR, A-TZ` — два типа с разными эталонами формы | `D1` |
| Нет проверяемой границы | «до черновика» — это состояние `draft`, достижимое любым непустым текстом | `D2` |
| Нет уровня оркестрации | между процессом и операцией нет узла, которому назначаются исполнитель и гейт | `D5` |

Общая форма ошибки одна: **список работ был назван процессом**. Список работ
отвечает на вопрос «чем занимается аналитик», процесс отвечает на вопрос «какое
состояние какого артефакта в каком состоянии оказывается по завершении». Первый
вопрос допускает перечисление, второй — нет.

## 2. Индустриальный базис: почему BABOK, а не собственная схема

Правило `T-4` мета-модели требует наследовать значение таксономии при наличии
индустриального источника. Для процессов бизнес-анализа таким источником
является BABOK Guide v3 (свод знаний, лежащий в основе сертификации CBAP):
<https://www.iiba.org/career-resources/a-business-analysis-professionals-foundation-for-success/babok/>.

Три причины, по которым базис берётся именно оттуда, а не строится заново.

| Причина | Формулировка |
| --- | --- |
| `B-1` Внешняя проверяемость | Утверждение «такого процесса в БА не существует» проверяется по внешнему источнику, а не мнением автора модели. |
| `B-2` Полнота покрытия | Шесть областей знаний покрывают весь цикл: от планирования анализа до оценки внедрённого решения. Собственная схема покрытие не гарантирует. |
| `B-3` Совместимость терминов | Разделение «бизнес-требования / требования заинтересованных сторон / требования к решению / переходные требования» уже разводит `BCREQ` и `ФТ`, то есть решает дефект `D1` внешней нормой. |

Шесть областей знаний BABOK Guide v3 (`L0`): **BAPM** — Business Analysis
Planning and Monitoring; **EC** — Elicitation and Collaboration; **RLCM** —
Requirements Life Cycle Management; **SA** — Strategy Analysis; **RADD** —
Requirements Analysis and Design Definition; **SE** — Solution Evaluation.

**Чем BABOK не является.** Области знаний — не фазы и не последовательность:
они выполняются параллельно и итеративно. Поэтому `L0` не может быть маршрутом
и не задаёт порядок; порядок появляется только на `L2`, где процесс привязан к
конкретному артефакту.

## 3. Дельта: что такое «процесс Манго КК» и почему он не совпадает с BABOK

Между `L0` и практикой контакт-центра лежат два разрыва.

**Разрыв гранулярности.** Задача BABOK `Specify and Model Requirements`
покрывает и функциональное требование к функции ВАТС, и раздел ТЗ по
ГОСТ 34.602-2020. Для агента это разные работы: разные эталоны формы, разные
критерии приёмки, разные гейты.

**Разрыв предмета.** В практике Манго КК существуют работы, которых в BABOK нет
как отдельной задачи, потому что они специфичны для модели поставки:
оценка внешнего тендерного ТЗ до принятия обязательств; формирование `BCREQ`
как самостоятельного документа обоснования изменения.

Отсюда правило дельты.

| Правило | Формулировка |
| --- | --- |
| `DL-1` | Процесс `L2` объявляется только при наличии родителя в `L0`; процесс без родителя — признак ошибки именования, а не новизны предметной области. |
| `DL-2` | Процесс `L2` объявляется отдельно от родителя только при наличии **разрыва**: гранулярности, предмета или формы. Разрыв называется явно в реестре. |
| `DL-3` | Дельта фиксирует различие, а не копию: если процесс `L2` совпадает с задачей `L0` по входу, выходу и критерию завершения, он не создаётся. |
| `DL-4` | Унаследованное имя процесса проходит поимённую проверку по `DL-1`–`DL-3`; непрошедшее переводится в реестр депрекации с указанием причины. |

## 4. Навык — подпроцесс, а не реализация операции

Действующая мета-модель объявляет `Skill` реализацией `Operation`
([`ba-meta-model/10-theory.md`](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/blob/main/research/ba-requirements/ba-meta-model/10-theory.md), §2)
и тем сводит иерархию к двум уровням. Онтология спицы при этом объявляет
сущность «Подпроцесс» с ребром `Процесс → Подпроцесс` (1→N), а ADR-009 спицы
называет шесть подпроцессов `П1`–`П6` и вешает на их границы три человеческих
гейта. Уровень существует в практике и отсутствует в модели (`D5`).

**Различающий вопрос.** Возьмём работу «сформировать вопросы Заказчику по
неразрешённым неоднозначностям». Она состоит из нескольких атомарных операций
(`check-ambiguity`, `generate-question`, `rank-items`), содержит условие
(вопрос формируется только для неоднозначностей выше порога значимости) и
завершается артефактом, который предъявляется человеку. Ни одна атомарная
операция её не описывает, а процессом она не является: собственного целевого
документа у неё нет, она обслуживает процесс выявления.

| Утверждение | Формулировка |
| --- | --- |
| `SB-1` | Навык — подпроцесс: именованная последовательность операций с собственными входом, выходом и гейтом. |
| `SB-2` | Отношение уровней: `Process → Skill (1:N) → Operation (1:N)`. Процесс оркеструет навыки; навык оркеструет операции. |
| `SB-3` | Навык принадлежит ровно одному процессу. Повторное использование выражается вызовом, а не вторым владельцем: два процесса, которым нужна одна работа, вызывают один навык, не копируя его. |
| `SB-4` | Навык — наименьшая единица, которую можно целиком поручить актору (человеку или агенту) и целиком проверить гейтом. Операция гейта не имеет: она проверяется контрактом выхода. |
| `SB-5` | Навык допускает ветвление внутри себя; операция — нет. Это и есть машинный признак различения уровней. |
| `SB-6` | Навык — единица компиляции в исполняющую среду: `SKILL.md` Execution Package соответствует навыку, а не операции. |

**Что стало с прежним значением слова.** Прежнее «навык = реализация операции»
не исчезает: реализация операции существует, но она является **свойством**
операции (её исполнителем и промптом), а не отдельной сущностью. Имя `Skill`
закрепляется за подпроцессом, потому что именно этот уровень компилируется в
исполняемый артефакт среды.

## 5. Процесс как контракт состояния, а не как список работ

| Правило | Формулировка |
| --- | --- |
| `PR-1` | Процесс объявляет вход: класс артефакта и его состояние жизненного цикла. |
| `PR-2` | Процесс объявляет ровно один **целевой** класс выхода. Побочные артефакты (`A-TRACE`, `A-REP`) объявляются отдельной строкой и целевыми не считаются. |
| `PR-3` | Процесс объявляет критерий завершения как переход целевого артефакта в объявленное состояние, подтверждённый гейтом. Слова «черновик», «готово», «оформлено» критерием не являются. |
| `PR-4` | Процесс объявляет владельца-родителя в `L0` и разрыв по `DL-2`. |
| `PR-5` | Процесс объявляет состав навыков `L3` и допустимые переходы между ними. |

Проверка `PR-2` на унаследованном примере: `fr-generation` объявлял выход
`A-FR, A-TZ`. По `PR-2` это два процесса. Разделение не является
терминологической придиркой: `A-FR` проверяется по ISO/IEC/IEEE 29148:2018
(характеристики качества требования), `A-TZ` — по ГОСТ 34.602-2020 (структура
документа). Один гейт не может проверять оба контракта.

## 6. Маршрут как ориентированный граф

Действующая формулировка «маршрут неизменен внутри прогона» описывает маршрут
как линейную последовательность (`D8`) и потому запрещает то, что происходит в
каждом реальном прогоне: обнаружение неоднозначности при нормализации обязано
направлять работу в формирование вопросов Заказчику.

| Утверждение | Формулировка |
| --- | --- |
| `RG-1` | Маршрут — ориентированный граф: вершины — навыки, рёбра — переходы, условия рёбер вычисляются на гейтах. |
| `RG-2` | Прогон — одна траектория в графе маршрута: последовательность фактически пройденных вершин и рёбер. |
| `RG-3` | Выбор ветви по результату гейта — **исполнение** маршрута. Маршрут при этом не меняется. |
| `RG-4` | Изменением маршрута является изменение множества вершин, рёбер или условий. Оно версионируется и происходит между прогонами, а не внутри. |
| `RG-5` | Граф маршрута ацикличен по умолчанию; цикл допускается только явно объявленным ребром возврата с условием выхода из цикла (например, «не более `N` итераций уточнения»). |

`RG-1`–`RG-5` заменяют формулировку §6 таблицы напряжений
[`ba-meta-model/10-theory.md`](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/blob/main/research/ba-requirements/ba-meta-model/10-theory.md);
согласование с мета-моделью выполнено в её версии 0.2.

## 7. Исполнимость агентом как критерий включения

Процесс, который нельзя ни поручить агенту, ни проверить машинно, в таксономии
допустим, но обязан быть помечен. Критерий берётся из шкалы механизмов
контроля `G1`–`G7`
([`research/ai-education/task-processing/20-taxonomy.md`](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/blob/main/research/ai-education/task-processing/20-taxonomy.md), §3).

| Правило | Формулировка |
| --- | --- |
| `AE-1` | Для каждого навыка процесса объявлены вход, выход, гейт и ярус контроля `G1`–`G7`. |
| `AE-2` | Необратимое действие (согласование с Заказчиком, перевод артефакта в `approved`, отправка вовне) удерживается ярусом не ниже `G5` — человеческим гейтом. |
| `AE-3` | Обратимая ошибка удерживается ярусом `G1`–`G2`; вынос её на `G5` — симметричная ошибка, превращающая мандат в инструкцию. |
| `AE-4` | Навык, для которого не удаётся объявить машинно проверяемый выход, помечается `Actor=human` и остаётся в модели: пропуск такой работы делает маршрут неполным. |

## 8. Границы теории

- Базис взят из одного свода знаний (BABOK Guide v3). Совместимость с IREB
  CPRE и SWEBOK не проверялась и вынесена в
  [`50-open-research.md`](https://github.com/G-Ivan-A/hybrid-Intelligence-lab/blob/main/research/ba-requirements/ba-process-taxonomy/50-open-research.md).
- Уровни `L2` и `L3` выведены из предметной области Манго КК и подтверждены
  синтетическими кейсами, а не статистикой прогонов: исторический корпус не
  использовал словарь процессов (`D7`) и потому не может служить основанием.
- `RG-5` (запрет неявных циклов) — проектное решение, а не следствие
  индустриальной нормы; его цена — необходимость объявлять предел итераций.
