# Теория `M2`: рендер, проекция, недрейф

## 1. Рендер как операция

**Определение.** Рендер — это тотальное отображение подмножества ядра в
документ заданной формы, при котором каждое утверждение документа имеет
прообраз в ядре.

Формально: `render(core, form, filter) → doc`, где каждый смысловой фрагмент
`doc` трассируется к элементу `core`. Отсутствие прообраза — дефект, а не
обогащение.

### 1.1 Пять инвариантов рендера

| № | Инвариант | Формулировка | Проверяемость |
| --- | --- | --- | --- |
| `RN-1` | Прообраз | каждое утверждение документа ссылается на элемент ядра | машинная |
| `RN-2` | Полнота фильтра | все элементы, попадающие под объявленный фильтр, вошли в документ | машинная |
| `RN-3` | Сохранение модальности | «обязан» не превращается в «желательно» и наоборот | полумашинная |
| `RN-4` | Пришпиленность версии | документ несёт `(core.id, core.version)` | машинная |
| `RN-5` | Согласованность веера | два документа одной поставки не противоречат друг другу по общему элементу | машинная при `RN-1` |

`RN-5` — производный инвариант: если оба документа соблюдают `RN-1`, общий
элемент физически один, и противоречие возможно только через нарушение `RN-3`.
Это и есть механизм, которого не хватает 23 прогонам корпуса с веером выходов.

### 1.2 Чем рендер не является

- Не редактурой смысла: перефразирование, меняющее модальность, — нарушение `RN-3`.
- Не дописыванием пропущенного: обнаруженный пробел возвращается в `M1`, а не
  заполняется на месте (правило `M2-R1`).
- Не согласованием: статус принадлежит элементу ядра (`AS-*` модуля `M1`).

## 2. Проекция

**Проекция** — форма подачи одного и того же утверждения для конкретной
аудитории и формы. Ключевое свойство: проекция **не имеет собственной
истинности**. Если проекция утверждает больше прообраза — это дрейф; если
меньше — это легальное сокращение, обязанное быть объявленным.

| Тип операции проекции | Легальность | Условие |
| --- | --- | --- |
| Отбор (подмножество элементов) | легальна | фильтр объявлен |
| Переупорядочивание | легальна | безусловно |
| Агрегация нескольких элементов в один абзац | легальна | все прообразы перечислены |
| Переформулировка без смены модальности | легальна | `RN-3` соблюдён |
| Уточнение числа, срока, условия | **нелегальна** | возврат в `M1` |
| Введение нового утверждения | **нелегальна** | дефект `DR-1` |

## 3. Недрейф как задача

Инвариант `K5` RFC требует, чтобы смысл не изменялся на границе `M1`/`M2`.
Задача делится на три различимые части, которые в практике смешивают:

1. **Дрейф добавления** — в документе есть то, чего нет в ядре.
2. **Дрейф потери** — из ядра выпало то, что должно было войти по фильтру.
3. **Дрейф искажения** — прообраз есть, но смысл изменён.

Первые два разрешимы машинно и полностью (`RN-1`, `RN-2`). Третий — не
разрешим полностью ни машинно, ни человеком: это задача семантической
эквивалентности. Честная позиция модуля: **`M2` гарантирует отсутствие
дрейфа добавления и потери и лишь снижает вероятность дрейфа искажения.**

### 3.1 Почему это не пессимизм

Из девяти прогонов корпуса с `hallucinations_shipped > 0` все девять —
дрейф добавления. Полностью разрешимый машинно класс покрывает наблюдаемую
проблему целиком; неразрешимый класс в корпусе не наблюдался, потому что не
было ядра, относительно которого его можно было бы заметить.

## 4. Индустриальные основания

| Источник | Что даёт `M2` | Ограничение |
| --- | --- | --- |
| ISO/IEC/IEEE 29148:2018 | структуры StRS/SRS/SyRS, характеристики документа как множества | описывает документ, не его порождение |
| ГОСТ 34.602-2020 | обязательный состав разделов ТЗ на АС | жёсткая форма, нет понятия источника |
| ГОСТ 34.601-90 | стадийность, определяющая момент поставки | — |
| ISO/IEC/IEEE 15289:2019 | номенклатура информационных продуктов жизненного цикла | каталог, не механика |
| Volere | шаблон карточки требования с атрибутами | уровень элемента, не документа |
| Cockburn | формы записи сценариев (`uc`) | только сценарии |
| DITA/DocBook, single-source publishing | зрелая индустриальная механика «один источник → много выходов» | из технической документации, не из БА |
| ReqIF / OSLC RM | обмен требованиями с сохранением идентичности | формат, не проверка смысла |
| StrictDoc, Doorstop, Sphinx-Needs | рабочая реализация «требования как исходный код → рендер» | сообщество мало́, русскоязычных форм нет |

**Ключевая асимметрия.** Механика single-source publishing решена в
технической документации (DITA) и в requirements-as-code (StrictDoc), но в
методологии БА отсутствует: BABOK и 29148 говорят, каким должен быть документ,
и молчат о том, как он порождается без потери. Вклад Хаба — перенос механики
single-source в контур БА и добавление проверки недрейфа.

## 5. Гипотезы

| № | Гипотеза | Метод опровержения |
| --- | --- | --- |
| `H2.1` | весь наблюдаемый вымысел — дрейф добавления, ловится `RN-1` | разметка 9 прогонов на классы дрейфа |
| `H2.2` | детерминированный рендер невозможен для `tz` в силу требований к связному тексту | попытка построить шаблон ТЗ по ГОСТ 34.602-2020 из ядра |
| `H2.3` | гибридный режим даёт основной выигрыш при минимальной цене | сравнение трёх режимов на одной задаче |
| `H2.4` | навязанные формы систематически беднее ядра | разметка форм заказчиков |
| `H2.5` | 40,4 % веера содержат хотя бы одно расхождение между документами | попарная сверка выходов 23 прогонов |
| `H2.6` | пришпиленность версии (`RN-4`) дешевле всех прочих проверок и даёт наибольший эффект | пилот |

## 6. Точки решения

- `D-2.1`: считать ли переформулировку без смены модальности легальной по
  умолчанию (принято: да, §2).
- `D-2.2`: где живёт проверка недрейфа (принято RFC `Q-2`, вариант «а»: в `M2`).
- `D-2.3`: обязателен ли машиночитаемый след прообраза в самом документе
  (принято: да для `L2`/`L3`, см. `30-decision-framework.md`).
