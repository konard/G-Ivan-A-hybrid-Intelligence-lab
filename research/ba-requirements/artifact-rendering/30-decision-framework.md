# Рамка решений `M2`: контракт `C-OUT`, проверка недрейфа, гейт `HG-5`

## 1. Контракт `C-OUT`

```yaml
out:
  id: OUT-2026-0031            # идентификатор поставки
  version: 2                   # версия поставки
  core_ref:                    # обязательная пришпиленность (RN-4)
    id: CORE-2026-0031
    version: 5
  route_ref: RK-2026-0031      # маршрутный лист M4
  mode: hybrid                 # RM-1 | RM-2 | RM-3
  trace_level: TR-2            # TR-0..TR-3
  documents:
    - id: DOC-1
      class: DC-1              # класс документа
      form: fr                 # ось A1
      audience: [AUD-2, AUD-3]
      filter:                  # объявленный фильтр (RN-2)
        scope: ["payments"]
        element_types: [EL-2, EL-4]
        status_min: AS-3
      preimages:               # прообразы (RN-1)
        - { fragment: "3.2", elements: ["FR-014", "FR-015"] }
      reductions:              # объявленные сокращения (PJ-6)
        - { element: "FR-021", reason: "форма CF-1 не имеет колонки критериев", annex: "annex-1" }
  drift_check:
    added: 0                   # DR-1
    lost: 0                    # DR-2
    modality_flags: 2          # DR-3, требуют человека
    checked_at_core_version: 5
  gate:
    hg5:
      owner: "руководитель направления"
      decision: approved
      basis: "A6 = external-contract"
```

### 1.1 Условия приёмки `C-OUT`

| № | Условие | Проверка |
| --- | --- | --- |
| `CO-1` | `core_ref` заполнен и указывает на существующую версию ядра | машинная |
| `CO-2` | `drift_check.added = 0` | машинная |
| `CO-3` | `drift_check.lost = 0` | машинная |
| `CO-4` | каждый смысловой фрагмент каждого документа имеет запись в `preimages` при `trace_level ≥ TR-2` | машинная |
| `CO-5` | все элементы фильтра имеют статус не ниже `status_min` | машинная |
| `CO-6` | каждое сокращение объявлено в `reductions` и имеет приложение | машинная |
| `CO-7` | `modality_flags` разобраны человеком до закрытия гейта | человек, факт фиксируется |
| `CO-8` | `mode` допустим для уровня `A3` по правилу `M2-R2` | машинная |
| `CO-9` | `checked_at_core_version = core_ref.version` | машинная |

`CO-9` — защита от кейса `C1-5` модуля `M1`: проверка недрейфа, выполненная над
устаревшей версией ядра, не считается выполненной.

## 2. Проверка недрейфа: механика и её предел

**Процедура `ND`.**

```
1. Взять C-CORE.version, зафиксировать множество E элементов под фильтром.
2. Для каждого документа разобрать на смысловые фрагменты (заголовок, пункт,
   строка таблицы, ячейка формы).
3. added  := фрагменты без записи в preimages           → DR-1
4. lost   := элементы E, не встречающиеся ни в одном preimage → DR-2
5. modality_flags := фрагменты, у которых модальный маркер
   отличается от модальности прообраза по словарю модальностей → DR-3
6. Для веера: элементы, встречающиеся в >1 документе, сверить
   попарно на совпадение модальности и числовых значений → DR-5
7. Отчёт записывается в drift_check контракта C-OUT.
```

**Предел процедуры, объявленный честно.** Шаги 3, 4, 6 полны и разрешимы. Шаг 5
опирается на словарь модальностей («обязан», «должен», «может», «желательно»,
«не допускается») и на числовые значения; он **не** обнаруживает искажение,
выраженное перефразированием без модальных и числовых маркеров. Такое
искажение остаётся зоной человека, и `CO-7` требует явно зафиксировать, что
человек её просмотрел. Утверждать, что `M2` гарантирует недрейф полностью,
было бы неверно; `M2` гарантирует отсутствие двух из трёх классов дрейфа.

## 3. Применение осей

| Ось | Влияние на `M2` |
| --- | --- |
| `A1` | задаёт множество классов `DC-*` и форм; `custom-form` включает механику `CF-*` |
| `A2` | контекст определяет обязательные приложения: `tender-rfp` требует таблицы соответствия форме, `paid-change` — раздела границ работ |
| `A3` | `L1` → `TR-1`, любой режим; `L2` → `TR-2`, `RM-1`/`RM-3`; `L3` → `TR-3`, `RM-1`/`RM-3`, `CO-7` с подписью |
| `A4` | `manual-stepwise` — сборка по документу с остановками; `autonomous-oneshot` — вся поставка разом, но `ND` обязателен до показа человеку; `hybrid` — остановка только при `modality_flags > 0` |
| `A5` | глубина `us+uc` расширяет множество `DC-3`/`DC-4` в поставке |
| `A6` | определяет владельца `HG-5` и необходимость подгейта `HG-5.1` |

**Ответ на `OQ-7` (кто отвечает за формат поставки при внешнем контуре).**
При `A6 = external-contract` формат поставки — предмет договора, поэтому
ответственность несёт владелец `HG-5` (руководитель направления), а не
аналитик; при `A6 = regulated` формат фиксируется до начала работ на `HG-0` и
изменению в ходе поставки не подлежит.

## 4. Гейты

| Гейт | Смысл | Машинная предусловие | Владелец по `A6` |
| --- | --- | --- | --- |
| `HG-5` | приёмка поставки | `CO-1`…`CO-6`, `CO-8`, `CO-9` выполнены | `internal` → БА; `external-contract` → руководитель направления; `regulated` → руководитель + профильный контроль |
| `HG-5.1` | подтверждение внешней передачи | `HG-5` закрыт, `CO-7` разобран, приложения по `A2` приложены | тот же, кто закрыл `HG-5`, отдельным действием |

**Почему `HG-5.1` отделён.** Приёмка документа и его отправка вовне — разные
решения с разной обратимостью. Принятый документ можно переделать; отправленный
заказчику — нет. Совмещение этих решений и есть механизм, по которому вымысел
покидает контур.

## 5. Алгоритм рендера

```
1. Принять C-CORE; проверить CC-1..CC-9 (иначе отказ, возврат в M1).
2. Прочитать маршрутный лист C-RK: A1..A6, требуемые формы.
3. Для каждой формы выбрать класс DC-* и режим RM-* по правилу M2-R2.
4. Объявить фильтр (scope, element_types, status_min = AS-3 по умолчанию).
5. Если форма навязана (CF-*): построить двустороннюю карту
   «поле формы ↔ атрибут элемента» ДО сборки (см. §6).
6. Собрать документ, фиксируя preimages по мере сборки, а не после.
7. Выполнить процедуру ND.
8. added>0 или lost>0 → сборка не принимается, дефект устраняется;
   утверждение без прообраза НИКОГДА не легализуется задним числом —
   оно возвращается в M1 как новый элемент (правило M2-R1).
9. modality_flags>0 → человек разбирает; решение фиксируется.
10. Закрыть HG-5, при внешней передаче — HG-5.1.
11. Передать C-OUT в M3.
```

## 6. Навязанные формы: двусторонняя проверка (`RQ-2.8`)

**Правило `M2-R4`.** Карта соответствия формы и ядра строится в обе стороны и
до сборки:

- **Прямая проверка (форма → ядро):** каждое поле формы имеет источник в ядре
  либо помечается как пробел. Пробел — вопрос заказчику, а не место для
  правдоподобного текста. Именно здесь возникали 37 неподтверждённых строк
  `RUN-0057`.
- **Обратная проверка (ядро → форма):** каждый элемент ядра под фильтром либо
  попадает в поле формы, либо объявляется в `reductions` с приложением.

**Правило `M2-R5`.** Если форма беднее ядра, недостающее выдаётся приложением;
молчаливое отбрасывание (`DR-7`) запрещено. Ответ на `RQ-2.7`: форма
ограничивает **поставку**, но не ядро и не обязательства.

## 8. Build vs buy

| Кандидат | Что закрывает | Вердикт |
| --- | --- | --- |
| StrictDoc | ядро как исходник, рендер в HTML/PDF/ReqIF, трассируемость | кандидат №1 совместно с `M1`; требует пилота на ГОСТ-форме |
| DITA + DITA-OT | зрелый single-source publishing, условная сборка | избыточен для БА, высокая цена входа |
| Sphinx-Needs | требования в тексте, фильтры, трассировка | кандидат для внутренних форм |
| Шаблонизаторы (Jinja, docxtpl) | механика `RM-1` для ГОСТ-форм | инструмент, а не решение; нужен свой слой прообразов |
| Pandoc | конвертация форматов поставки | вспомогательный |
| Средства проверки цитат/атрибуции | шаг 5 процедуры `ND` | зрелых готовых нет; собственный словарь модальностей |

**Собственная разработка неизбежна** в одном месте: слой `preimages` и
процедура `ND`. Ни один готовый инструмент не проверяет соответствие
сгенерированного документа набору требований по смыслу.
